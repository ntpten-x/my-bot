# เปิดใช้การดึงโพสต์ต่อเนื่อง v1.11.0

เอกสารประจำรุ่น 1.11.0 — การแก้หลังตรวจ production และขั้นตอนเปิดใช้รุ่นถัดไปอยู่ใน [รุ่น 1.11.1](RELIABILITY-FIXES-1.11.1.th.md)

อัปเดตเว็บและส่วนขยายเป็นชุดเดียวกันก่อนใช้งาน รุ่นนี้บันทึกโพสต์เป็นชุดและเก็บแท็บไว้เมื่อหมดงบต่อช่วง เพื่อกลับมาอ่านต่อ ขอบเขตเก็บย้อนหลังยังไม่เกิน 24 ชั่วโมง ต้องเปิด Chrome เครื่องต้องไม่ sleep และ Facebook ต้องเข้าสู่ระบบ

**สถานะเครื่องที่ตรวจ:** doctor พบ DATABASE_URL ยังเป็น SQLite เดิม ต้องใส่ DATABASE_URL และ DIRECT_URL ของ Supabase Postgres ใน `.env` ก่อนรัน migration/seed และเปิดแอป ไม่มีการแก้ค่าลับให้โดยอัตโนมัติ และไม่มีเว็บฟังพอร์ต 8001 ระหว่างตรวจนี้

## เริ่มใช้งานหลังอัปเดต

1. ตรวจ `.env` ให้ใช้ Supabase Postgres ตาม [คู่มือติดตั้ง](SETUP.th.md) ถ้าเครื่องยังใช้ SQLite ให้ตั้งค่าการเชื่อมต่อจริงก่อน แล้วรัน `npm run db:migrate` และ `npm run db:seed` ตามคู่มือ งานดึงโพสต์รอบนี้ไม่มี migration หรือ dependency ใหม่
2. รัน `npm run build` แล้วเริ่มเว็บและ worker ใหม่ด้วย `npm run start:prod` ตามวิธีเปิดแอปเดิม
3. ไป `chrome://extensions` แล้วกด Reload ของ MY-BOT หากติดตั้งจาก ZIP ให้ใช้ไฟล์จากเว็บที่อัปเดตแล้ว เปิด popup ตรวจว่าเป็น **1.11.0**
4. เปิด Facebook ใน Chrome ที่จับคู่ไว้ ไปหน้าแหล่งข้อมูล เปิดกลุ่มที่ต้องการ และดูภาพรวมระบบว่ารับ heartbeat รุ่นใหม่แล้ว
5. ในหน้าตั้งค่า “โพสต์ต่อชุดบันทึก” เป็นขนาดชุด ไม่ใช่เพดานหยุดอ่าน ค่าเริ่มต้น 40 ใช้ได้ตามเดิม ความลึกเป็นงบก่อนสลับกลุ่ม
6. ตรวจค่าพักเมื่อใช้งาน Facebook ช่วงเวลาพัก และพักเมื่อหน้าจอล็อกให้ตรงการใช้งานของคุณ รุ่นนี้รักษาค่าพักเดิมทุกค่า

นัดอ่านต่อประมาณ 30 วินาทีเป็นเวลาเข้าคิว ไม่ใช่คำรับรองว่าจะเริ่มภายใน 30 วินาทีเสมอ งานกลุ่มอื่น ช่วงพัก เครื่อง sleep และการหน่วงของ Chrome ทำให้ช้ากว่านี้ได้

## อ่านสถานะอย่างไร

- **limit / yield:** ยังไม่ครบ เก็บแท็บแล้วนัดอ่านต่อ
- **loading:** ฟีดยังแสดงการโหลด เก็บสถานะและเว้นระยะก่อนลองใหม่
- **stalled:** ไม่มีความคืบหน้าหรือโหลดบางเกินไปหลังการกู้คืน ยังไม่เรียกว่าเก็บครบ
- **exhausted:** ไม่พบ key เพิ่มหลังลองปลุกและเลื่อนซ้ำ หรือหน้าแสดงจบฟีดซ้ำสองครั้ง เป็นผลสังเกตรอบนั้น ไม่ใช่หลักฐานว่า Facebook แสดงทุกโพสต์ในกลุ่ม
- **old:** พบขอบเขตอายุที่กำหนด ไม่ส่งโพสต์เก่าเข้าระบบ
- **logged_out / checkpoint:** เจ้าของต้องเข้าสู่ระบบหรือตรวจสอบบัญชีเอง ระบบไม่พยายามข้าม

ภาพรวมระบบเพิ่มโพสต์ใหม่ต่อนาทีอ่าน จำนวนรอบยังไม่ครบ/ผิดพลาด ข้อมูลรอส่ง อายุข้อมูลค้าง และจำนวนแท็บเก็บตำแหน่งไว้ กลุ่มที่เลยเวลานัดแสดงจำนวนและเวลารอนานสุด อัตราต่อนาทีใช้ผลรวมเวลาอ่าน ไม่ใช่อัตราส่งจากทั้งเครื่องต่อเวลาจริง และ inserted ต่อรอบอาจต่ำกว่าข้อมูลเข้าจริงหาก heartbeat เป็นผู้ระบายคิวภายหลัง

## การกู้คืนและขอบเขตทรัพยากร

อ่านจริงพร้อมกันสูงสุด 2 แท็บ ลดเหลือ 1 ขณะตามเก็บหรือ Chrome หน่วง เก็บตำแหน่งฟีดค้างได้ 20 แท็บ เมื่อช่องเต็ม กลุ่มอื่นยังได้อ่านหัวฟีดด้วยแท็บชั่วคราว แต่รอช่องว่างก่อนรักษาตำแหน่งระยะยาว เพื่อไม่ไล่ปิดตำแหน่งของทุกกลุ่มจนไม่มีใครอ่านจบ

ถ้า Chrome ทิ้งแท็บหรือเจ้าของปิด Chrome ตำแหน่ง DOM จะหาย ระบบกู้ pending ที่ยังไม่เข้า outbox และเริ่มรอบตามเก็บใหม่โดยไม่หยุดที่ known ด้านบน แท็บค้างที่เก่าเกิน 2 ชั่วโมงถูกเก็บกวาด ข้อมูลรอส่งไม่ถูกลบทิ้งเพื่อเปิดช่อง ข้อมูล outbox ที่ผิดพลาดถาวรหรือเกินอายุยังคงอยู่ให้เจ้าของตรวจ

การส่งมีโอกาสซ้ำเมื่อระบบหยุดระหว่าง checkpoint กับ receipt จึงใช้ stable keys และการตัดซ้ำฝั่งรับ ความถูกต้องที่ตั้งใจคือไม่ลบข้อมูลที่ยังไม่มี receipt ไม่ได้อ้างว่า HTTP ถูกเรียกเพียงครั้งเดียว

## หลักฐานและการตรวจซ้ำ

ผลตรวจสุดท้าย: 489 tests ผ่าน 88 ข้ามตามเงื่อนไข (รวม DB integration ที่ไม่มี TEST_DATABASE_URL), production build และ git diff check ผ่าน

```powershell
npm.cmd test
npm.cmd run build
node scripts/audit-scrape-local.cjs
```

`tests/extension/continuous-reader.test.ts` รัน readFeed / scrapeGroup / outbox / checkpoint จริงกับ Chrome transport จำลอง ครอบคลุมเกิน 200 โพสต์, resume, timeout, snapshot ใหญ่, reload ได้คนละชุด, MV3 restart, browser restart, storage failure, network outage, pause, outbox blocked, login/checkpoint และ empty feed ที่ยืนยันแล้ว

`tests/pipeline/scrape-continuation.test.ts` ตรวจนัด 30 วินาทีโดยไม่มี jitter, loading backoff, hints กลุ่มลำดับที่ 25 และเพดาน query พร้อมกัน พร้อม metrics สรุป

ตรวจใน Chrome โปรไฟล์แยกด้วย Playwright และ `scripts/verify-continuous-reader-browser.js`: DOM จำลองเปลี่ยนจาก p:101–103 เป็น p:104–106 โดยคง count=3 และ height=6016 ระบบตรวจ growth ได้ใน 354 ms เลื่อนจริง 800 px เก็บครบ 6 และไม่มี page error ไม่ได้เข้าบัญชี Facebook จริงหรือส่งคอมเมนต์

ฐานข้อมูลจริงยังอ่านไม่ได้ด้วย PrismaClientInitializationError; doctor ระบุสาเหตุว่า DATABASE_URL ยังใช้ SQLite เดิม (env-db-kind, db และ token ไม่ผ่าน) จึงยังไม่มีตัวเลข throughput/ความครบจากกลุ่มจริงหรือผล soak test 24 ชั่วโมง ชุด DB integration ข้ามเมื่อไม่มี TEST_DATABASE_URL โดยไม่ใช้ production แทน ต้องตรวจ heartbeat และสถิติหลังเปิดใช้จริงก่อนสรุปความครบในกลุ่มของเจ้าของ

หากต้องย้อนกลับ ให้พักส่วนขยายก่อน แล้วใช้เว็บและ extension รุ่นก่อนหน้าคู่กัน อย่าล้าง storage ของส่วนขยายขณะที่ยังมีข้อมูลรอส่ง
