# ผลตรวจการดึงโพสต์ 7 พฤศจิกายน 2026

เอกสารนี้เป็นผลตรวจก่อนแก้ ดูพฤติกรรมรุ่นใหม่และขั้นตอนเปิดใช้ใน [ผลการแก้ไข v1.11.0](SCRAPE-FIXES.th.md)

ตรวจโค้ดปัจจุบันในเครื่อง รวมงานที่แก้ค้างไว้ ไม่ได้เปลี่ยนพฤติกรรมตัวดึงโพสต์

## ข้อสรุป

ระบบมี scheduler, adaptive interval, recovery, outbox และการจำกัด concurrency แต่ยังไม่ตรงเป้าหมายอ่านต่อเมื่อมีโพสต์จนไม่มีโพสต์ใหม่ในช่วงเวลาที่กำหนด การเพิ่มเพดานอย่างเดียวไม่แก้ปัญหาการกลับไปอ่านจากด้านบน

## สิ่งที่ควรแก้ตามลำดับ

1. **ต่อรอบอ่านจากตำแหน่งเดิม** — ตอนนี้ชน cap/scroll/time budget แล้วปิดแท็บ รอบใหม่เปิดจากด้านบน และหยุดเมื่อเจอโพสต์เดิมต่อกัน ควรส่งเป็นชุดพร้อมบันทึกความคืบหน้าและอ่านต่อในแท็บเดิมขณะที่ยังพบโพสต์ใหม่ แบ่งเวลาให้กลุ่มอื่นด้วย เมื่อแท็บหายต้องมีเส้นทางกู้ coverage ที่ไม่หยุดกับ known keys บริเวณหัวฟีด
2. **อย่าถือ cap ว่าเก็บครบ** — `isIncompleteScrape` ยกเว้น cap และ config ถือ cap เป็น reachedKnown ทำให้ไม่ขอตามเก็บส่วนตกค้าง ค่าเริ่มต้นใน settings คือ 40 โพสต์ต่อรอบ เพดานสูงสุด 200
3. **รวมผลก่อนและหลัง reload** — `scrapeGroup` เลือก run ที่ found มากกว่า โดยไม่ได้รวม fresh ของทั้งสองรอบ โพสต์ที่พบเฉพาะรอบที่ถูกทิ้งจึงไม่ได้ส่ง ควรรวมตาม stable post key ก่อนส่งและแยก metrics ของแต่ละ pass
4. **แยกหมดเวลาออกจากจบฟีด** — `readFeed` ตั้ง stoppedBy=limit เมื่อหมดเวลา แต่ไม่ได้ตั้ง hitLimit ทำให้เงื่อนไข retry/incomplete อาจไม่ทำงานหากพบแล้วอย่างน้อย 3 โพสต์ ควรส่งสถานะ incomplete ให้ตรงกันทั้ง extension และ server
5. **นิยาม end ให้ตรวจสอบได้** — การไม่พบ key ใหม่ 5 หน้าจอเป็นเพียงสัญญาณว่าไม่มีความคืบหน้า อาจเป็นโหลดค้าง ไม่ใช่หลักฐานว่า Facebook ไม่มีโพสต์ ต้องแยก no-progress, loading, logged-out, checkpoint และ exhausted พร้อม recovery ที่จำกัดครั้ง
6. **ตรวจลำดับฟีดก่อนใช้ known/old streak** — URL ขอ chronological แต่ไม่มีการยืนยันว่าหน้าแสดงตามนั้นจริง การพบโพสต์เดิม 3 โพสต์หรือโพสต์เก่า 3 โพสต์จึงอาจหยุดก่อนโพสต์ที่ยังไม่เก็บ โหมดตามเก็บควรใช้เงื่อนไขเข้มกว่ารอบตรวจโพสต์ใหม่
7. **วัดและจัดคิวอย่างเป็นธรรม** — orderDueGroups ให้ needsCoverage มาก่อนทุกครั้ง กลุ่มอื่นอาจรอนานหากกลุ่มที่อ่านไม่ครบมีมาก ควรมี aging หรือสัดส่วนสำหรับกลุ่มที่รอนาน ติดตาม overdue สูงสุด, fresh/นาที, inserted/fresh, incomplete, outbox อายุเก่าสุด และความสำเร็จในการกู้หลัง Chrome หยุด worker

## พฤติกรรมที่แนะนำ

พบโพสต์ใหม่ → บันทึกและส่งชุดย่อย → อ่านต่อ; ชนงบต่อช่วง → พักให้กลุ่มอื่นและต่อจากเดิม; ยืนยันว่าไม่มีความคืบหน้าหลัง recovery → รอตรวจรอบถัดไป; เครือข่ายล่ม → เก็บ outbox และส่งซ้ำตาม receipt; คิวเต็ม → หยุดรับเพิ่มโดยแสดงสาเหตุ

รักษาช่วงอายุโพสต์ไม่เกิน 24 ชั่วโมงตามนโยบายปัจจุบัน รักษาการอ่านผ่าน UI และข้อจำกัด concurrency ไม่ปิด timeout ทั้งหมด ไม่แตะระบบส่งคอมเมนต์

Chrome ต้องเปิด เครื่องต้องไม่ sleep และบัญชี Facebook ต้องยังเข้าสู่ระบบ ค่า quiet_pause_on_facebook เริ่มต้นเป็น true จึงพักเมื่อเจ้าของใช้งาน Facebook ตามเงื่อนไข quiet ต้องตรวจค่าจริงให้ตรงความต้องการ

## การตรวจยืนยัน

- tests/extension/scrape.test.ts, tests/pipeline/scrape-plan.test.ts, tests/pipeline/scrape-hints.test.ts ผ่าน 35/35
- scripts/audit-scrape-local.cjs ทำซ้ำ cap และการเลือกทิ้งผลหนึ่งในสอง pass ได้โดยไม่แก้ฐานข้อมูล
- อ่านสถิติฐานข้อมูลไม่สำเร็จด้วย PrismaClientInitializationError ทั้งในและนอก sandbox จึงยังไม่มีผลวัด throughput หรือ coverage จากระบบจริง
- ไม่ได้ทดสอบ Facebook จริงหรือยืนยันว่า extension ที่ Chrome โหลดตรงกับไฟล์ใน workspace

ก่อนประกาศว่าทำงานต่อเนื่องได้ ต้องทดสอบฟีดจำลองที่มีโพสต์เกิน cap, reload ได้คนละชุด, หมดเวลาที่ยังมีโพสต์, DOM virtualization, network outage, Chrome restart และหลายกลุ่มที่มี backlog พร้อมกัน แล้ววัดการทำงานจริงอย่างน้อย 24 ชั่วโมง
