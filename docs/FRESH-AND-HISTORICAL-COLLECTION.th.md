# ตรวจโพสต์ล่าสุดระหว่างอ่านย้อนหลัง — Extension 1.11.6

## วิธีทำงาน

บอทยังคงอ่านโพสต์ย้อนหลังตามอายุที่ตั้งไว้ สูงสุด 24 ชั่วโมง โดยเก็บแท็บและจุดอ่านค้างไว้ เมื่อกลับมาทำงานกลุ่มนั้น หากผ่านอย่างน้อย 60 วินาทีจากการตรวจด้านบนครั้งก่อน จะเปิดแท็บชั่วคราวตรวจด้านบนฟีดก่อน แล้วปิดแท็บชั่วคราวและอ่านย้อนหลังต่อจากจุดเดิม ไม่เลื่อนแท็บย้อนหลังกลับขึ้นบนและไม่เริ่มย้อนหลังใหม่ทุกครั้ง

งานตรวจล่าสุดอ่านด้านบนและเลื่อนเพิ่มได้ไม่เกินสองครั้ง จำกัดเวลาสูงสุด 20 วินาทีต่อครั้ง โดยสำรอง 25 วินาทีจากงบปกติ 45 วินาทีให้งานย้อนหลัง หากงบเหลือน้อยกว่า 35 วินาที จะให้งานย้อนหลังทำต่อในรอบนั้น รอตรวจล่าสุดในรอบที่มีเวลาพอ การตรวจทำตามลำดับ ไม่เพิ่มเพดานงานอ่านที่กำลังทำพร้อมกัน ไม่สลับแท็บเจ้าของ ตาม [การแยกหน้าต่างอ่านข้อมูล](BACKGROUND-COLLECTION.th.md)

ค่า 60 วินาทีเป็นเกณฑ์ถึงเวลาตรวจซ้ำ ไม่ใช่ SLA รับโพสต์ภายในหนึ่งนาที เมื่อมีหลายกลุ่ม ต้องรอคิวอย่างเป็นธรรมตามระบบเดิม และ Facebook/Chrome อาจโหลดช้า ตรวจล่าสุดไม่หยุดทันทีเมื่อพบโพสต์ที่รู้จัก เพื่อมองผ่านโพสต์เก่าที่ปักไว้ด้านบนด้วย ใช้ URL เรียงตามเวลาแบบเดิมที่ Facebook รองรับ หาก Facebook ไม่แสดงโพสต์นั้นในหน้าโหลด การอ่าน DOM ไม่สามารถรับประกันว่าจะเก็บครบทุกโพสต์ได้

หลังอัปเดตเว็บและรีสตาร์ต ให้ Reload MY-BOT ใน `chrome://extensions` เป็น **1.11.6** ไม่ต้องจับคู่ใหม่ ไม่ต้องเปิดกฎคอมเมนต์เพิ่ม ผลการอ่านกลุ่มจะแสดงข้อความ `ตรวจโพสต์ล่าสุด เก็บใหม่ …` เมื่อได้ทำการตรวจล่าสุดในรอบนั้น

## สรุปปัญหาและสาเหตุ

เจ้าของพบว่าบอทสนใจโพสต์ย้อนหลังจนไม่เก็บโพสต์ใหม่ ระบุสาเหตุใน `extension/background.js`: `scrapeGroup()` เดิมเรียก `loadContinuation()` ทุกครั้ง และอ่าน DOM ที่เลื่อนลงไปแล้วต่อจนจบ แม้แยกงานเป็นช่วงสั้นและเวียนคิวกลุ่ม แต่ไม่มีขั้นตอนกลับไปตรวจด้านบนระหว่างนั้น โพสต์ที่เพิ่มหลังเริ่มอ่านจึงอยู่นอกเส้นทาง DOM ที่กำลังอ่าน

การจำลองด้วยฟีด 100 หน้าจอ เพิ่มโพสต์ `999` ที่ด้านบนหลังจบรอบแรก แล้วขยับเวลา 61 วินาที ทำให้เห็นข้อผิดพลาดซ้ำได้แน่นอน โพสต์ใหม่นั้นไม่ถูกส่งเข้า ingest ขณะ cursor ย้อนหลังยังเดินต่อ การทดสอบใช้แหล่งเดียวและ key ใหม่ ตัดสาเหตุการแย่งคิวข้ามกลุ่มและ dedupe ฝั่งเซิร์ฟเวอร์สำหรับอาการนี้ ไม่ได้เชื่อม debugger ไป Chrome เจ้าของ ใช้ VM รันฟังก์ชันจริงและจำลองเฉพาะ Chrome/HTTP

## การแก้ไข

แก้ใน working tree ของ branch `master`: แยกตัวประสาน `scrapeGroup()` กับ `scrapeGroupPass()` ให้ตัวแรกแบ่งเวลาระหว่าง latest/history และตัวหลังใช้เส้นทางอ่าน/ตรวจบัญชี/หยุด/ส่ง outbox เดิม งานตรวจด้านบนไม่สร้าง continuation และไม่เขียนทับ `coverageRecovery` หรือส่ง coverage report เพื่อไม่ให้ระบบเข้าใจว่าการอ่านย้อนหลังจบแล้ว

`headChecks` เก็บเวลาตรวจ และ `headRecovery` เก็บโพสต์ที่จับได้แต่ยังเขียน outbox ไม่สำเร็จ แยก key ตาม API base, บัญชี Facebook และ source URL ก่อนลบ headRecovery ต้องส่งต่อข้อมูลเข้าจุดกู้คืนย้อนหลังหรือคิวถาวรแล้ว การเปิด Chrome ใหม่จึงกู้โพสต์ล่าสุดที่จับได้แล้วได้ แม้แท็บชั่วคราวหายไป ใช้ post key/dedupe และ server receipts เดิมเพื่อไม่เพิ่มรายการซ้ำ ถ้าตรวจล่าสุดล้มเหลว จะรอรอบถัดไป ไม่เปิดแท็บซ้ำรัว ๆ; checkpoint/logout ยังหยุดตามข้อจำกัดบัญชีเดิม

## ช่องว่างเดิม

ชุดทดสอบการอ่านต่อเนื่องตรวจว่าอ่านย้อนหลังต่อได้และไม่ทำโพสต์ที่เห็นแล้วหาย แต่ไม่มีเหตุการณ์เพิ่มโพสต์ที่ด้านบนหลัง cursor ผ่านไปแล้ว จึงไม่พบความต่างระหว่างการอ่านย้อนหลังคืบหน้า กับความสดของข้อมูล

## การตรวจสอบ

`tests/extension/continuous-reader.test.ts` เพิ่ม regression สำหรับโพสต์ใหม่ระหว่างอ่านย้อนหลัง ตรวจว่าจุดย้อนหลังเดิมยังคืบหน้า, ไม่ส่ง coverage report จากงาน latest, ไม่เกินงบ 45 วินาที, ไม่เปิด latest ทุก tick, ยังคืบหน้าเมื่อเวลาน้อย, กู้โพสต์ latest หลังเขียนคิวล้มเหลวและ restart และอ่านผ่าน known head posts เพื่อเจอโพสต์ใหม่โดยไม่สร้างรายการซ้ำ

การทดสอบเป็นข้อมูลสังเคราะห์และ Chrome API จำลอง ไม่มีการดึง Facebook จริงหรือส่งคอมเมนต์จริง ต้องสังเกตอัตรารับโพสต์ใน Chrome เจ้าของหลัง Reload โดยเฉพาะกลุ่มที่โพสต์ถี่มากหรือโหลดฟีดช้า

ผลตรวจรอบแก้ไข: `npm test` ผ่าน **705 tests / 78 files** ด้วย Postgres ทดสอบแยกผ่าน `TEST_DATABASE_URL`, `npm run build` ผ่าน, `node --check extension/background.js` และ `git diff --check` ผ่าน
