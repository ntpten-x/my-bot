## สิ่งที่ควรแก้เรียงตามลำดับ

### 1. แก้การรอ AI เมื่อหมดโควตาก่อนเพิ่มกำลังเครื่อง

หลักฐานจาก `/api/ai-queue`: งาน pending แสดงว่า Groq และ Gemini อยู่ระหว่าง cooldown ถึง 8 พฤศจิกายน 00:00 UTC (07:00 น. ไทย), OpenRouter ชนขีดจำกัดที่ระบบตั้งไว้ 45 ครั้ง/วัน และ Cloudflare ชนขีดจำกัด 100 ครั้ง/วัน นี่คือค่าที่แอปแจ้ง ไม่ใช่การยืนยันโควตาสากลของบัญชีผู้ให้บริการ

เส้นทางโค้ดที่ตรวจ:

- `src/lib/ai/provider-registry.ts:routedClassifyAttempts` คืน skipped errors โดยไม่มีเวลาที่ลองได้ใหม่อย่างมีโครงสร้าง
- `src/lib/ai/run.ts:classifyLeads` ส่งเหตุผลเหล่านั้นกลับคิว
- `src/lib/ai/queue.ts:retry` เพิ่ม attempts ทุกครั้ง และให้ failed เมื่อครบ 10 แม้เหตุผลคือยังไม่มี provider ให้เรียก

**ข้อเสนอ:** แยก deferred เพราะ quota/cooldown ออกจาก actual call failure; นัดตาม provider ที่กลับมาพร้อมเร็วสุดและไม่เพิ่ม attempts หากยังไม่ได้เรียก AI จริง ใช้กฎชั่วคราวได้โดยรักษาสถานะรอ AI ไว้ ไม่กด retry failed ทั้งหมดซ้ำระหว่างที่โควตายังไม่พร้อม จากข้อมูลนี้ยังยืนยันไม่ได้ว่างาน failed เดิมทั้ง 126 งานเกิดจากสาเหตุเดียวกัน

### 2. แก้การไม่คืบหน้าของ feed และความเป็นธรรมของคิวอ่าน

หลักฐานจาก overview รุ่น 1.11.0: 6/6 รอบ incomplete, มี loading/stalled, เฉลี่ย 103 วินาที/รอบ และกลุ่มหนึ่งยังค้างผลล่าสุดที่ limit ขณะเลยนัดประมาณ 9 นาที ทั้งที่มี heartbeat ใหม่และอีกกลุ่มบันทึกเพิ่มได้ จึงไม่ใช่อาการเว็บหรือส่วนขยาย offline ทั้งระบบ

จุดที่ต้องพิสูจน์ด้วย DOM/telemetry เพิ่ม:

- `extension/background.js:readPage` ใช้ `[role="progressbar"], [aria-busy="true"]` ทั้ง document อาจจับสิ่งที่ไม่ใช่การโหลด feed เป็น loading ได้ ยังไม่มีการตรวจ DOM บัญชีจริงเพื่อยืนยันว่าเป็นสาเหตุรอบนี้
- `readFeed` ใช้ทั้งเวลาอ่านและรอบ recovery; `cycle` จำกัดงบก่อนเริ่มแต่ละกลุ่ม แต่ไม่ได้ส่งเวลาที่เหลือทั้งหมดลงไปจำกัด runPass และ retry กลุ่มที่เริ่มใกล้หมดงบยังใช้เวลาเพิ่มได้
- ระหว่าง needsCoverage อ่านทีละกลุ่ม การกู้รอบละหลายนาทีทำให้กลุ่มอื่นได้คิวช้า

**ข้อเสนอ:** จำกัด loading detector ภายใน feed ที่อ่านได้จริงและตรวจ visibility, แยกเหตุผลไม่คืบหน้า (ตำแหน่ง scroll, key delta, DOM count, loader, focus), ส่ง deadline ของ cycle ลงไปถึงทุก pass, จำกัด recovery ต่อช่วงให้สั้นแล้วหมุนไปกลุ่มอื่น พร้อมติดตามเวลาตั้งแต่ due จนเริ่มอ่านจริง ไม่ใช่เวลาที่ report เสร็จอย่างเดียว

### 3. ทำสถานะ AI ให้ตรงกับคิวจริง

ในช่วงเดียวกัน overview บอก Groq “ใช้งานได้ 996 ms” และ watchdog “พร้อม 2/4” แต่ `/api/health` บอก availableProviders=0 และคิวแสดง cooldown/quota

**ข้อเสนอ:** แยก “ทดสอบเชื่อมต่อสำเร็จ” จาก “เรียกใช้งานได้ตอนนี้หลังคำนึงถึงโควตา” โดยใช้ availability/cooldown แหล่งเดียวกับ worker แสดงเวลารีเซ็ตที่ตรงกัน ไม่ให้ไฟเขียวจากผล probe เก่ากลบเหตุที่คิวเดินไม่ได้

### 4. ติดตาม ingest และตรวจระยะยาวหลังแก้สองข้อแรก

เก็บ p50/p95 ingest พร้อม batch size และเวลา DB transaction เพื่อดูว่าคำขอเล็กเสีย overhead มากเพียงใด อย่าเพิ่มจำนวนแท็บหรือแก้เพดานโควตาโดยไม่รู้ขีดจำกัดจริงของบัญชี

ตรวจต่อเนื่อง 24 ชั่วโมง โดยมีเวลารอคิวรายกลุ่ม, รอบที่จบ verified boundary, outbox อายุเก่าสุด, actual AI calls เทียบกับ deferred และ post IDs ที่เจ้าของตรวจจาก Facebook เป็นชุดอ้างอิง ก่อนสรุปว่าเก็บครบได้กี่เปอร์เซ็นต์
