# ลดภาระระบบโดยรักษา flow เดิม

## ขอบเขต

ปรับเส้นทางร่วมของเว็บและ API การอ่านโพสต์ งานเปรียบเทียบโพสต์ซ้ำของ worker และตัวสังเกต DOM ของส่วนขยาย โดยไม่เพิ่ม dependency, migration หรือเปลี่ยนโควตา รอบเก็บข้อมูล กฎจัดหมวด การอนุญาตคอมเมนต์ และระบบ claim/lease

ใช้วิธีตัดงานที่ไม่จำเป็นและพักงานแสดงผลเมื่อซ่อนแท็บ ไม่เพิ่มแคชให้ข้อมูลควบคุมการส่งหรือเปลี่ยนตารางทำงานของบอต เพราะอาจทำให้คำสั่งควบคุมล่าช้า ข้อมูลที่ API ส่งให้หน้าเว็บยังคงรูปแบบเดิม ยกเว้นตัวเลือก `countOnly=1` ใหม่ที่แถบเมนูใช้เอง

## จุดที่ปรับ

| ส่วน | เดิม | หลังปรับ |
| --- | --- | --- |
| อ่านโพสต์ ฟีด ค้นหา แดชบอร์ด SSE และผลการแก้ไขโพสต์ | โหลด scalar ทุกคอลัมน์ รวม embedding และสถานะ worker | ใช้ `postSelect` เลือกเฉพาะฟิลด์ที่ serializer ใช้ โดยคง relations, OCR สำหรับข้อมูลติดต่อ และโน้ต |
| ตัวกรองจังหวัด `/api/meta` | Prisma `distinct` มีการ dedupe ฝั่ง client | `groupBy` รวมจังหวัดในฐานข้อมูล ส่งกลับหนึ่งแถวต่อจังหวัด |
| เมนูร่วมทุกหน้า | โหลดประวัติแจ้งเตือนสูงสุด 80 รายการทุกครั้งที่ต้องการแค่ยอดยังไม่อ่าน | ขอเฉพาะ `count` ผ่าน `countOnly=1`; หน้าแจ้งเตือนยังได้ประวัติเดิม |
| เมนู แดชบอร์ด ภาพรวม และหน้าบัญชี | บางหน้ามี interval ทำงานขณะซ่อนแท็บ | ใช้ refresh แบบ serial, ไม่มี wake timer เมื่อซ่อน และตรวจใหม่เมื่อกลับมาเห็นหน้า |
| ฟีด | เปิด SSE ใหม่เมื่อเปลี่ยนตัวกรอง/หน้า/ตั้งค่าเสียง และปล่อยคำขอเก่าจนจบ | เก็บ SSE เดิม อ่านตัวกรองล่าสุดผ่าน ref และ abort fetch ที่ถูกแทนที่/เมื่อออกหน้า |
| รูปในฟีดและรายการข้อความ | โหลดรูปนอกจอพร้อมกันและ decode ตามค่าเริ่มต้น | ใช้ native lazy loading และ asynchronous decoding พร้อมขนาดรูปเดิม; ตัวอย่างรูปที่กำลังแก้ไขยังโหลดทันที |
| แคช stats/overview/doctor | คำขอที่ช้ากว่า TTL ทำให้เริ่มงานซ้ำ | แชร์ promise ที่ยังไม่เสร็จ และเริ่มนับ TTL หลังอ่านสำเร็จ; error ยังคง retry ได้ |
| worker หาโพสต์ซ้ำ | คำนวณ SHA-256 ซ้ำสำหรับข้อความ normalized ของทุก neighbor | เทียบข้อความโดยตรง คงขอบเขตแหล่งข้อมูล อายุ ข้อความสั้น และการเลือกตัวแรก |
| ส่วนขยายเก็บโพสต์จากแท็บส่วนตัว | MutationObserver และ fallback timer ยังตื่นขณะซ่อน | disconnect observer และหยุด timer; กลับมาแล้วอ่าน DOM ใหม่ โดยไม่ล้าง pending/seen หรือ observedAt |

SSE ฝั่งเซิร์ฟเวอร์ยังคงส่งข้อมูลและใช้ cursor เดิม การแจ้งเตือนเมื่อมีโพสต์ใหม่ยังทำงานตามค่าของเจ้าของ การยกเลิก fetch ฝั่งเบราว์เซอร์ไม่รับประกันว่าจะยกเลิก query ที่เซิร์ฟเวอร์รับไปแล้ว ตัวอ่านที่บอตจัดการเองและงานคอมเมนต์ไม่ได้เปลี่ยนวิธีทำงาน

## หลักฐาน

เขียน regression tests และรันให้เห็นปัญหาก่อนแก้ ได้แก่ โหลดโพสต์เกินฟิลด์ที่ใช้, โหลดประวัติเพื่อเอาตัวเลขเดียว, โหลดซ้ำเมื่อแคชช้า, timer ในแท็บซ่อน, เปิด SSE ซ้ำ, ไม่ยกเลิก fetch เก่า และคำนวณแฮช 401 ครั้งสำหรับ neighbor 400 รายการ

ผลวัด CPU แบบจำลองชุดละ 40 โพสต์ เทียบ 400 neighbors ข้อความประมาณ 532 ตัวอักษร: การวัดแรกใช้เวลามัธยฐาน 54.563 ms ก่อนแก้ และ 0.164 ms หลังแก้ ตัดการคำนวณ SHA จาก 16,040 ครั้งเหลือ 0 และเทียบผลลัพธ์เดิม/ใหม่ตรงกัน 500 กรณี ตัวเลขนี้เฉพาะฟังก์ชันหาโพสต์ซ้ำ ไม่ใช่ความเร็วรวมของระบบหรือการรับรอง RAM/CPU ของเครื่องจริง

วัดซ้ำโดยไม่แตะฐานข้อมูลหรือ Facebook:

```bash
npx tsx scripts/benchmark-dedupe.ts
```

คำสั่งตรวจ:

```bash
npm test -- --maxWorkers=2
npm run build
```

การทดสอบฐานข้อมูลต้องมี `TEST_DATABASE_URL` แยกต่างหากเท่านั้น หากไม่มีจะข้ามตามกติกาเดิม การทดสอบ DOM ใช้ข้อมูลสังเคราะห์ ไม่มีการส่งคอมเมนต์จริง

ผลตรวจรอบสุดท้าย: ชุดทดสอบทั้งระบบผ่าน 886 รายการ ข้ามตามเงื่อนไข 136 รายการ รวม 135 ไฟล์ และไม่มี unhandled errors ชุดฟีด/ข้อความหลังปรับรูปผ่านเพิ่มอีก 16 รายการ และชุดอ่านข้อมูล/วงจรหน้าเว็บผ่าน 10 รายการ `npm run build` จบด้วย exit code 0 มี warning เดิมเรื่อง native `<img>` สองตำแหน่งและตัวแปร `_now` ที่ไม่ได้ใช้หนึ่งตำแหน่ง ไม่ได้ปรับส่วนส่งคอมเมนต์เพื่อแก้ warning นั้น ผู้ตรวจอิสระไม่พบ regression ระดับสูงหรือกลางใน diff ที่ปรับ

## ข้อจำกัดและการนำไปใช้

ผลปรับอยู่ในโค้ดของ workspace ต้องเริ่มเว็บ/worker จาก build ใหม่ และโหลดส่วนขยายใหม่เพื่อใช้ content script ที่ปรับแล้ว โดยแท็บ Facebook เดิมจะใช้ content script ใหม่เมื่อโหลดหน้านั้นครั้งถัดไป ไม่ได้ push, deploy, เปลี่ยนค่าบัญชี หรือเริ่มส่งคอมเมนต์

ยังไม่ได้วัดเวลาตอบสนองทุกหน้าบนฐานข้อมูลจริงหรือ RAM/CPU ของ Chrome/Windows ขณะใช้งานต่อเนื่อง ความช้าจากเครือข่าย Supabase จำนวนโพสต์จริง และ DOM ของ Facebook ต้องตรวจจากการใช้งานจริงเพิ่มเติม การสแกนฐานข้อมูลทั้งชุดในงาน maintenance และต้นทุนการ render รายการขนาดใหญ่ยังควรทำ profiling ต่อก่อนเปลี่ยนวิธีทำงาน
