# ทางเลือกสร้างรายได้จาก MY-BOT

ตรวจแหล่งข้อมูลและโค้ดเมื่อ 12 พฤศจิกายน 2026 เอกสารนี้เป็นข้อเสนอเชิงผลิตภัณฑ์ ยังไม่มีหลักฐานว่าลูกค้ายอมจ่ายหรือว่าความต้องการตลาดผ่านการยืนยัน ไม่ใช่ข้อสรุปทางกฎหมาย

## ข้อเสนอหลัก

เริ่มจากโครงการทดลองแบบเสียเงินกับธุรกิจเจ้าของคนเดียว 2–3 รายในหมวดเดียว โดยติดตั้งแยกรายและรับข้อมูลที่มีสิทธิใช้ชัดเจน ขายผลลัพธ์ว่า “คัดรายการภาษาไทยที่ควรติดตามและลดเวลาคัดมือ” พร้อมวัดผลจริง ก่อนลงทุนทำ SaaS หรือขายการคอมเมนต์อัตโนมัติเป็นจุดเด่น

Pipeline, scoring และ workflow มีผู้ขายรายใหญ่ทำอยู่แล้ว: HubSpot ระบุ deal scoring, pipelines และ sales workflows; HighLevel ระบุ CRM, pipelines และ workflow automation ดังนั้นข้อเสนอให้แข่งขันด้วยหมวดสินค้าไทยเฉพาะทาง การตั้งค่าหน้างาน และผลลัพธ์ที่ตรวจสอบได้ เป็นข้ออนุมานเชิงกลยุทธ์ ไม่ใช่ข้อพิสูจน์ว่ามีตลาดรองรับ ([HubSpot Sales Hub](https://www.hubspot.com/products/sales), [HighLevel Pricing](https://www.gohighlevel.com/pricing))

## ฐานผลิตภัณฑ์ปัจจุบันและช่องว่าง

- ระบบเป็นเจ้าของคนเดียว: `Owner` อยู่ใน [schema](../prisma/schema.prisma#L12); `createOwner` ปฏิเสธเจ้าของคนที่สอง และ `verifyPassword` ใช้ `findFirst` ใน [auth.ts](../src/lib/auth.ts#L39) จึงยังไม่ใช่ระบบบัญชีลูกค้าหลายองค์กร
- `Post` มี `pipelineStatus` และ `followUpAt` อยู่แล้ว แต่ schema ยังไม่มีโมเดล Deal/รายได้/tenant จึงควรต่อยอดการติดตามเดิมและเพิ่มหลักฐานผลลัพธ์ มากกว่าสร้าง CRM ใหญ่ใหม่ ([schema](../prisma/schema.prisma#L98))
- ตัวเลข `accuracy` ปัจจุบันเป็นสัดส่วนรายการที่ถือว่าตรวจแล้วแต่ไม่ถูกแก้ โดยการเปิดอ่านก็นับ reviewed จึงไม่ใช่ความแม่นยำจากชุดคำตอบอิสระ ([classification-stats.ts](../src/lib/classification-stats.ts#L16))
- สคริปต์ประเมินเตือนชัดว่าชุดข้อมูลแต่งขึ้นซึ่งเจ้าของยังไม่ตรวจ ห้ามอ้างเป็นความแม่นยำข้อมูลจริง ([evaluate-classifier.ts](../scripts/evaluate-classifier.ts#L14))

## ความเสี่ยงที่ต้องแก้ในข้อเสนอขาย

Meta ระบุว่าการใช้ automation เก็บข้อมูล Facebook โดยไม่ได้รับอนุญาตจาก Meta ขัดข้อกำหนด แม้ข้อมูลนั้นคนทั่วไปจะเปิดดูได้ การยินยอมของผู้ดูแลกลุ่มเพียงอย่างเดียวจึงไม่ใช่หลักฐานว่า Meta อนุญาต การใช้ DOM ที่มองเห็นแทน API ไม่ได้ลบประเด็นนี้ ([Meta: How We Combat Scraping](https://about.fb.com/news/2021/04/how-we-combat-scraping/))

การพึ่ง DOM ยังมีความเสี่ยงจากหน้าเว็บเปลี่ยน การเข้าถึงบัญชี และข้อมูลไม่ครบ จึงไม่ควรรับประกันอ่านครบทุกโพสต์หรือพบผู้ซื้อทันที ข้อเสนอ paid pilot ควรเริ่มจาก CSV/ข้อความที่ลูกค้ามีสิทธิใช้ แบบฟอร์มรับ lead ของลูกค้า หรือ official API ที่ตรวจสิทธิและเงื่อนไขของ use case นั้นแล้วเท่านั้น เอกสารนี้ไม่ได้ยืนยันว่า official API รองรับการอ่าน Facebook Groups การใส่ข้อมูลด้วยมือก็ไม่ทำให้สิทธิในข้อมูลเกิดขึ้นเอง

ไม่ใช้การส่งคอมเมนต์จริงเป็นกิจกรรมทดลองตลาดโดยปริยาย ต้องมีอนุมัติแยกชัดเจนตามกติกาโครงการ และยังต้องพิจารณาเงื่อนไขแพลตฟอร์ม ไม่ขายคำสัญญาว่าคอมเมนต์ได้ไม่จำกัดหรือไม่มีความเสี่ยงบัญชี

## โมเดลรายได้สามแบบ

| แบบ | ผู้จ่ายและสิ่งที่ซื้อ | เงื่อนไขก่อนเริ่ม |
| --- | --- | --- |
| ติดตั้งและดูแลรายเครื่อง | เจ้าของร้านจ่ายค่าตั้งค่า + ค่าดูแลรายเดือน เพื่อคัด lead/แจ้งติดตามในหมวดเดียว | เหมาะเริ่มที่สุด; แยก app, database, secrets, API keys, browser profile และ backup ของแต่ละราย ไม่แชร์ Supabase ของเจ้าของเดิม |
| บริการคัดรายการพร้อมผู้ตรวจ | ร้านหรือทีมขายจ่ายรายรอบ/ตามปริมาณที่ตกลง รับรายการที่ตรวจแล้วจากข้อมูลที่มีสิทธิใช้ | วัดเวลาคนตรวจและกำไรจริง จำกัดขอบเขตงาน ไม่ขายฐานข้อมูลบุคคลที่เก็บมาโดยไม่มีสิทธิ |
| SaaS เฉพาะหมวด | องค์กรจ่ายค่าสมาชิก + usage โดยใช้ input ที่ได้รับอนุญาต | ทำเมื่อ pilot แสดงการต่ออายุ: ต้องมี tenant identity, authorization ทุกเส้นทาง, worker/queue/storage/cache/export/backup isolation และทดสอบข้าม tenant; เปิด RLS อย่างเดียวไม่พิสูจน์ว่าข้อมูลแยกครบ |

ไม่จำเป็นต้องตั้งราคาถาวรก่อนคุยลูกค้า หากทดสอบราคา ให้ระบุว่าเป็นสมมติฐานและเสนอขอบเขตงาน/เพดานปริมาณแน่นอน เช่น ค่าติดตั้งหนึ่งครั้งและค่าทดลอง 30 วัน โดยตรวจว่าราคาเกินต้นทุนบริการจริง ไม่ใช้ราคาคู่แข่งเป็นหลักฐาน willingness to pay ของ MY-BOT

## การตรวจตลาดและเกณฑ์ตัดสินใจ

ข้อเสนอต่อไปนี้เป็นเกณฑ์ทดลอง ไม่ใช่สถิติที่เกิดขึ้นแล้ว:

1. สัมภาษณ์ร้านในหมวดเดียว 8–10 ราย ขอให้เล่ากระบวนการล่าสุด เวลาใช้จริง โอกาสที่หลุด และแหล่งข้อมูลที่มีสิทธิใช้ จากนั้นเสนอ pilot ขอบเขตเดียวกัน ไม่ถามเพียงว่า “สนใจไหม”
2. เก็บ baseline 7 วัน แล้วทดลอง 30 วันกับ 2–3 รายที่ชำระเงินจริง วัดนาทีคัดข้อมูลต่อวัน อัตราติดตามทันเวลา จำนวน lead ที่ตรวจว่าเข้าเกณฑ์ และผลติดต่อ/เสนอราคา/ปิดงานที่เจ้าของยืนยัน
3. วัดคุณภาพด้วยชุดข้อมูลจริงที่มีสิทธิใช้และติดป้ายด้วยคน แยกชุดปรับกฎกับชุดวัดผล รายงาน precision ของ buyer, recall บนชุดที่ตรวจครบ, false positive และ unknown พร้อมจำนวนตัวอย่าง ห้ามใช้ correction proxy แทน accuracy
4. วัดความน่าเชื่อถือ: สัดส่วนนำเข้ารับสำเร็จ งานตกค้าง อายุรายการก่อนพร้อมใช้ และเวลาช่วยเหลือต่อลูกค้า ระบุว่าความหน่วงจาก capture ไม่ใช่เวลาจากการเผยแพร่โพสต์
5. เกณฑ์เดินหน้าตัวอย่าง: อย่างน้อย 2 รายยอมต่ออายุในราคาที่ครอบคลุมต้นทุน และเวลาคัดลดลงอย่างน้อย 30% เทียบ baseline โดยคุณภาพผ่านเกณฑ์ที่ตกลง หากไม่ผ่าน ให้ปรับหมวด/ข้อเสนอหรือหยุดขยาย ไม่เพิ่มฟีเจอร์เพื่อกลบหลักฐาน

ยอดขายที่เกิดระหว่าง pilot ยังไม่พิสูจน์ว่าระบบเป็นสาเหตุ ควรแยกรายได้ที่เจ้าของยืนยัน รายได้คาดการณ์ และรายการที่อ้างอิงผลไม่ได้

## ต้นทุนต่อราย

`ต้นทุนต่อเดือน = hosting + database/storage/backup + AI + notifications + ค่าแรง support + ค่าแรงตรวจข้อมูล + ค่าบำรุง collector ที่เฉลี่ยต่อราย + ค่ารับชำระ`

`AI = Σprovider[(input_tokens × input_rate + output_tokens × output_rate) / 1,000,000] + embedding/OCR + ต้นทุน retry`

`กำไรส่วนเกินต่อราย = รายได้ประจำสุทธิ − ต้นทุนผันแปรต่อราย`; บันทึกค่าติดตั้งและชั่วโมง onboarding แยกเพื่อไม่ให้รายได้ครั้งเดียวบดบังการขาดทุนประจำ ส่วนค่าเครื่อง/ไฟ/เวลาบำรุง local AI ยังต้องคิด แม้ไม่มีค่าบริการต่อ token ใช้อัตราจริงจากบัญชี ณ เวลาทดลอง ไม่สมมติราคา API หรือ quota ฟรีคงที่

## สี่ฟีเจอร์แรกที่ควรทำเมื่ออนุมัติ pilot

1. นำเข้าข้อมูลที่ได้รับอนุญาตแบบ CSV/ข้อความ/ฟอร์ม พร้อมที่มา เวลานำเข้า และหลักฐานสิทธิที่เหมาะสม ใช้ pipeline เดิมเพื่อเทียบคุณภาพได้
2. บันทึกผลการขายขั้นต่ำต่อรายการ: contacted/qualified/quoted/won/lost, เหตุผล และมูลค่าที่เจ้าของยืนยัน พร้อม export ไม่ต้องเริ่มด้วยบัญชีหรือ CRM เต็มรูปแบบ
3. คิวตรวจ buyer และบันทึกคำตอบคน เพื่อวัด precision/recall แยกจากสถิติเปิดอ่าน และใช้ปรับหมวดเฉพาะลูกค้า
4. หน้ารายงาน pilot: baseline เทียบผลจริง เวลาที่ประหยัด ต้นทุน AI/ชั่วโมงดูแล งานผิดพลาด และวันหมดอายุ/ลบข้อมูล เพื่อคุยต่ออายุจากหลักฐาน

เอกสารนี้ไม่ได้เปลี่ยนโค้ดหรือเปิด automation ใด ๆ ยังไม่ได้สัมภาษณ์ลูกค้า ทดสอบความเต็มใจจ่าย หรือยืนยันสิทธิ API สำหรับกรณีใช้งานเฉพาะ
