# ปรับประสิทธิภาพคิวคอมเมนต์ — Extension 1.11.4

## สรุปและสาเหตุ

ก่อนแก้ คำขออนุญาตที่ใช้เวลา 4 วินาทีทำให้ client ไม่เรียกปุ่มส่ง แต่รายงาน `uncertain` แล้ว server พักทั้งระบบ อีกทั้งสำเร็จแล้วก็รายงานซ้ำใน `finally` ทุกงาน การรับงานไม่ตรวจโควตาจนกว่าจะเปิดแท็บและเตรียมข้อความแล้ว และการสแกนครอบคลุมโพสต์ตั้งแต่เริ่มระบบโดยไม่จำกัดกลุ่ม/อายุ

การแก้ใน working tree `master` (ยังไม่มี commit/PR) อยู่ที่ `extension/comment-worker.js`, `src/lib/auto-comment/browser.ts`, `src/lib/auto-comment/dispatch-budget.ts` และ API comments โดยคง durable sending markers, generation/revision fencing และอายุสิทธิ์ไม่เกิน 3 วินาที

## สิ่งที่เปลี่ยน

1. แยก journal เป็น `claimed`, `authorizing` และ `sending` ช่วง authorizing ยังไม่สามารถเรียกปุ่มส่งได้ ถ้าคำขอช้า/สูญหายหรือหยุดก่อนเรียกปุ่ม จะรายงาน `not_sent` แทนการพักระบบ งานที่ได้สิทธิ์แล้วคงประวัติ dispatch และไม่ถูกส่งใหม่อัตโนมัติ หากเริ่มเรียก send แล้วผลไม่ชัดเจนยังคงเป็น `uncertain`
2. ตรวจโควตารวมและระยะพักกลุ่มก่อน claim จึงไม่เปิดแท็บเมื่อยังไม่มีงานที่ส่งได้ คิวเลือกข้ามกลุ่มที่ติดพักไปหากลุ่มที่พร้อมในชุดที่ตรวจได้ไม่เกิน 30 งานต่อคำขอ และตรวจโควตาซ้ำภายใต้ control lock ก่อนออกสิทธิ์จริง
3. เวลารออิงระยะพักที่เหลือ จุดคืนโควตารายชั่วโมง และเที่ยงคืนไทยของรายวัน แทนการบวก 60 วินาทีทุกกรณี การเลื่อนหลายงานในกลุ่มเดียวกันรวมเป็น updateMany ลดคำสั่งซ้ำ เมื่อเจ้าของปรับโควตาจะปลุกเฉพาะงานที่ยังรอ โดยไม่กด Start หรือเปลี่ยน generation ให้เอง
4. สแกนเฉพาะ source IDs ที่อยู่ในกฎที่เปิด ยินยอม และผูกบัญชี/อุปกรณ์แล้ว กรองอายุจาก postedAt หรือ createdAt เมื่อไม่มีวันที่โพสต์ ตามอายุสูงสุดของกฎที่เปิด ถ้าไม่มีกฎพร้อมจะไม่รัน SQL สแกน fingerprint/checkpoint ยังคงใช้กับโพสต์ที่เข้าเงื่อนไขเพื่อจับการแก้ข้อความ ผล AI และข้อมูลแหล่ง
5. เส้นทางปกติส่ง report ครั้งเดียว เก็บผลรายงานที่ต้องส่งไว้ใน journal ก่อนเรียกเครือข่าย หากรายงานล้มเหลวจะลองรายงานผลเดิมใน recovery ไม่เรียกปุ่มส่งซ้ำ Server ตอบรับผลเดิมซ้ำได้โดยไม่สร้าง log ซ้ำหรือเปลี่ยนผล terminal และ client ไม่ลบ journal เพียงเพราะ HTTP 200 หากยังไม่ได้รับ `ok: true`

## วิธีอัปเดต

อัปเดตเว็บ/worker ก่อน แล้วไป `chrome://extensions` กด Reload MY-BOT เป็น **1.11.4** ในทุกโปรไฟล์ที่ใช้ Server ไม่แจกงานหรือออกสิทธิ์ใหม่ให้ protocol เก่า แต่ยังรับ report รุ่นเก่าเพื่อปิดประวัติงานค้าง การ Reload ไม่เปิดปุ่มรับงาน ไม่เปิดกฎ และไม่กดเริ่มส่งแทนเจ้าของ

ไม่เพิ่มตารางหรือ migration การทดสอบและการติดตั้งโค้ดไม่ได้เปลี่ยนโควตา สถานะหยุดฉุกเฉิน หรือกฎของเจ้าของ

## การพิสูจน์และการตรวจสอบ

ก่อนแก้ regression tests ให้ผล:

- สำเร็จแล้วมี report สองครั้ง แทนหนึ่งครั้ง
- authorize ช้า 4,000 ms มี send 0 ครั้ง แต่รายงาน uncertain สองครั้ง
- กลุ่มที่ยังต้องพัก 30 วินาทีกลับได้รับ claim
- โพสต์นอกกลุ่มที่เลือกและโพสต์หมดอายุสร้าง checkpoint รวม 2 รายการ

หลังแก้ `TEST_DATABASE_URL` ชี้ PostgreSQL ทดสอบที่พอร์ต 55439 เท่านั้น แต่ละ suite ใช้ disposable test_* schema `npm run test:ci` ผ่าน **692 tests / 77 files** รวมการข้ามกลุ่มติดพัก การตรวจโควตาซ้ำหลัง claim การกู้ journal การตอบรับ report ซ้ำ การไม่ rearm dispatch key และการปลุกคิวหลังเพิ่มโควตา `npm run build` ผ่าน ไม่ส่ง Facebook จริง

การทดสอบเดิมรับรองรายงานซ้ำสองครั้งไว้โดยตั้งใจและเน้นว่าไม่ส่งซ้ำ มากกว่าทดสอบคำขอช้าก่อนเรียก send จึงไม่พบการพักระบบเกินจำเป็น เพิ่ม regression ตามเงื่อนไขเหล่านี้แล้ว

## ข้อจำกัดที่ยังคงไว้

- ถ้าเริ่มเรียก send แล้วผลหาย ยังต้องตรวจเองและไม่ส่งซ้ำอัตโนมัติ
- ถ้า browser/server ขาดการติดต่อจน sending lease หมด และยังไม่ยืนยันว่าปุ่มไม่เคยถูกเรียก Server ต้องรักษา `uncertain` และหยุดรอตรวจ ไม่คลายสถานะคลุมเครืออัตโนมัติ
- สิทธิ์ที่ออกไปแล้วอาจกดส่งต่อได้ถึง 3 วินาทีหลัง Stop ไม่มีการขยายสิทธิ์จากเวลาที่ได้รับ response
- โควตานับการออกสิทธิ์เป็นความพยายามส่ง รวม not_sent ที่ได้สิทธิ์แล้ว ไม่คืนโควตาอัตโนมัติ
- สถานะ not_sent เป็นประวัติที่ไม่ลองส่งโพสต์เดิมใหม่อัตโนมัติ งานที่ถูกเลื่อนก่อนออกสิทธิ์ยังรอส่งได้ตาม retryAt
- ยอดตรวจพบ/ผลประเมินใหม่จำกัดเฉพาะกลุ่มและอายุที่เข้าเงื่อนไข ไม่ใช่ยอดโพสต์นำเข้าทั้งระบบ
- ยืนยันพฤติกรรมด้วย mock และฐานข้อมูลแยก ยังไม่ได้ benchmark อัตราสำเร็จบน Facebook จริงหรือรับประกันว่าจะส่งได้ครบ 200 ต่อวัน
