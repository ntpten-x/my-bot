# การแก้คอมเมนต์และคิวอ่าน — Extension 1.11.35

## สรุป

แก้การตรวจรุ่นโค้ดที่ Chrome รันจริง การอ่านหลักฐานคอมเมนต์ อายุโพสต์ และคิวอ่านข้อความเต็ม หลังผู้ใช้อนุญาตให้แก้และใช้งานในทุกกลุ่มปัจจุบันที่เปิดใช้งาน จำนวน 10 กลุ่ม บัญชี คำสำคัญ ข้อความ ระยะพัก 60 วินาทีต่อกลุ่ม และโควตา 60/ชั่วโมง 1,440/วันคงเดิม

## อาการและหลักฐาน

รอบตรวจ 13:21–13:41 น. วันที่ 14 พ.ย. 2026 รับ 35 โพสต์ ประเมินข้าม 29 รอข้อความเต็ม 5 และตรงกฎ 1 งาน มี dispatch หนึ่งครั้งแต่ผล `uncertain` และไม่มี remoteCommentId จึงยังอ้างว่าส่งสำเร็จไม่ได้

ตรวจ Chrome ตัวที่ใช้งานจริงผ่าน debugger ที่ loopback ชั่วคราว พบว่า manifest แจ้ง 1.11.32 แต่ `MyBotCommentWorker.run` ไม่มีการนัดปลุกตามคิว และ `saveFullTextBacklog` ไม่มี review queue ของโค้ดรุ่นใหม่ ภายในมี 199 รายการหมดอายุและตัวนับ overflow 399 ขณะที่ heartbeat เก่าขาดฟิลด์เหล่านี้แล้วถูกแสดงเป็นศูนย์ หลัง `chrome.runtime.reload()` ตรวจโค้ดทั้งสองฟังก์ชันใหม่ได้ตรงกับไฟล์ทันที

หลังโหลดโค้ดใหม่จริง ผลส่งยังคลุมเครือ จึงพักส่งและตรวจงานถัดไปที่อยู่ใน allowlist ทีละงาน ไม่ส่งซ้ำงานเดิม พบข้อความใน DOM หลังคลิก ช่องพิมพ์ว่าง และลิงก์ผู้เขียนแบบ `/profile.php?id=<own-account>&comment_id=<receipt>` ภายใน comment article ไม่มี `data-commentid` รูปแบบนี้ต่างจาก permalink ของโพสต์ที่ตัวตรวจเดิมยอมรับ ระหว่าง reconcile ตัวอ่านเปลี่ยนจากกรอบที่เตรียมไว้ไปยัง article ที่ไม่มีข้อความดังกล่าว

การเปิดโพสต์ใหม่แบบอ่านอย่างเดียวไม่พบข้อความเดิมใน DOM ที่โหลดครั้งนั้น ไม่ใช้การไม่พบนี้เป็นหลักฐานว่า Facebook ไม่เคยรับคอมเมนต์ เพราะอาจมีการกรองหรือการแสดงผลไม่ครบ และไม่แก้สถานะงานเก่าเป็นสำเร็จโดยอนุมาน

## สาเหตุ

1. ตรวจการอัปเดตจาก `chrome.runtime.getManifest().version` เพียงอย่างเดียว ซึ่งไม่ยืนยันว่า service worker และ `importScripts` ที่กำลังทำงานเป็นโค้ดใหม่ การคัดลอกไฟล์และ restart Chrome ครั้งก่อนจึงยังยืนยันการอัปเดตได้ไม่ครบ
2. `browser-comment.js::links` รับเฉพาะ comment URL ที่ pathname เป็นโพสต์ปัจจุบัน จึงตัด profile locator ที่มี comment_id แม้อยู่ในกรอบคอมเมนต์และเป็นบัญชีเจ้าของ `reconcile` ยังแทนที่กรอบเดิมที่เชื่อถือได้ด้วยกรอบแคบกว่า
3. baseline เดิมไม่เก็บ `data-commentid` ที่ยังไม่มี anchor และเทียบ URL ทั้งเส้น การเปลี่ยน tracking อาจทำให้คอมเมนต์เดิมดูเหมือนคอมเมนต์ใหม่ การจับข้อความแบบ substring และการรวม parent comment กับ nested reply ยังเสี่ยงยืนยันผิดคน
4. Worker ไม่ส่ง reason ของ observation ไปพร้อม report จึงเหลือเพียง uncertain โดยแยกเหตุไม่ได้
5. SQL รับเฉพาะโพสต์ที่เก็บเข้าหลังเริ่มรอบอยู่แล้ว แต่ยังมี `before_start` ตรวจเวลาเผยแพร่ซ้ำ ทำให้โพสต์ที่อายุผ่าน maxAgeHours ถูกข้าม
6. Metrics นับ review/expired เป็น remaining และเอาอายุของงานเหล่านั้นมารวมกับคิวรอทำ อีกทั้ง detail slice ก่อน discovery ถูกข้ามเมื่อมีหลายกลุ่มครบกำหนด จึงเสี่ยงอดทำงานต่อเนื่อง

## การแก้

- กำหนด build ในโค้ด background/sender/observer แยกจาก manifest ส่ง `X-Extension-Runtime` และ heartbeat build เซิร์ฟเวอร์ไม่ออก claim/grant หาก build ไม่ตรง ส่วน report เก่ายังรับได้ ไม่ทิ้ง journal ใช้ marker นี้ตรวจปัญหา cache ในการปฏิบัติงาน ไม่อ้างว่าเป็น cryptographic attestation
- หน้า readiness แสดงโค้ดเก่าหรือรุ่นไม่ทราบ และแสดง active/review/blocked แยกกัน ฟิลด์ที่ client เก่าไม่ส่งเป็น unknown ไม่สมมติศูนย์
- รับ own-profile locator เฉพาะ HTTPS Facebook ที่ตรวจบัญชีตรงแล้ว ภายในกรอบโพสต์ที่ผ่านการตรวจ พร้อมข้อความตรง ผู้เขียนตรง และ receipt ใหม่ แล้วสร้างลิงก์บน canonical post เดิม ไม่เรียก private API ไม่เพิ่ม click หรือใช้การกดซ้ำ
- คงกรอบที่เตรียมไว้ระหว่าง reconcile เมื่อ session และโพสต์ยังตรง และหาใหม่เฉพาะเมื่อกรอบเดิมหาย คำตอบ observe ที่ยืนยันได้ยังเป็นการพบใน DOM ไม่ใช่การรับรองจาก Meta API
- บันทึก baseline ด้วย comment ID รวม data-commentid ไม่ใช้ tracking เป็นตัวแยก ตรวจข้อความตรงและขอบเขตผู้เขียนโดยไม่รวม nested replies
- ส่ง reason ผ่าน report/journal/audit ทั้งกรณีผลไม่ชัดเจนและกรณียืนยันว่าไม่ได้กด เมื่อ state ก่อน click เปลี่ยน รายงาน not_sent แทนการเดาว่าส่งแล้ว ไม่มี retry งานที่ออก grant หรือคลุมเครือ
- ใช้ maxAgeHours กับเวลาเผยแพร่ โดยคงเกณฑ์ createdAt หลังเริ่มรอบ เปลี่ยน policy fingerprint ให้ประเมิน checkpoint ใหม่ แต่คง live dedupe keys และ terminal jobs ทุกแถว
- กัน detail slice 10–15 วินาทีก่อน discovery แม้หลายกลุ่มครบกำหนด และแยก remaining/oldestAge เฉพาะ active work รายการหมดอายุรอตรวจยังเก็บไว้ ไม่เปิด retry กลุ่มนี้เอง

## ขั้นตอนอัปเดตและข้อจำกัด

คัดลอกไฟล์ public ของ Extension โดยเก็บ install-config/profile เดิม รีสตาร์ตเว็บและ worker ที่เป็นของ MY-BOT โหลด Extension ใหม่จริง แล้วตรวจ manifest, runtime build, sender build, observer build และ header ให้ตรง 1.11.35 ก่อน resume การ restart Chrome หรือดูเลขเวอร์ชันอย่างเดียวไม่เพียงพอ

Debugger ชั่วคราวต้องปิดหลังตรวจ โดยถอด drop-in ของ MY-BOT ที่สร้างเพื่อวินิจฉัยและ restart workstation ขณะพักส่ง ไม่เปิดพอร์ต debug สู่เครือข่าย ไม่เก็บ credentials หรือ raw DOM ในเอกสารนี้

การส่งยังต้องมีโพสต์ที่ผ่านกฎ ระยะพักเป็นขั้นต่ำต่อกลุ่ม ไม่รับรองว่าจะมีโพสต์ผ่านทุกหนึ่งนาที ไม่แก้ผล uncertain เก่าโดยเดา และไม่รับรองความคงอยู่ของคอมเมนต์หรือ soak ระยะยาวจากการทดสอบสั้น

ผลตรวจ Facebook จริงระหว่างรุ่น 33/34: ตัวตรวจอ่านข้อความตรงและบัญชีตรง แต่ลิงก์มี `comment_id=client:<uuid>` ซึ่งเป็นรายการชั่วคราว ไม่ใช่ numeric receipt และ **ต้องไม่ยืนยันสำเร็จ** ตรวจแบบอ่านอย่างเดียวเฉพาะคำขอที่หน้า Facebook สร้างจาก click ปกติ พบ HTTP 200 แต่ response ระบุ `code=1390008`, `severity=CRITICAL`, `is_transient=false`, หัวข้อ “คุณไม่สามารถใช้ฟีเจอร์นี้ได้ในขณะนี้” ตัวข้อความที่ UI ส่งมีความยาว 4 ตัวอักษรและตรงข้อความที่ตั้งไว้ ค่า input ไม่มี actor_id จึงไม่ใช้การขาดฟิลด์นี้กล่าวอ้างว่าบัญชีไม่ตรง ไม่เก็บ cookies/token/ตัวคำขอหรือ response ทั้งก้อน และไม่เรียกหรือ replay private API

จึงเพิ่มเหตุผล `observation_temporary_receipt` แยกจาก receipt_missing และยังไม่รับรหัส client เป็นผลสำเร็จ คงผล uncertain ทุกงาน ไม่บังคับเปลี่ยนเป็นส่งสำเร็จ พัก control และกฎด้วยเหตุผล Facebook จำกัดฟีเจอร์ พร้อมเก็บคิวรอไว้ ไม่ทดสอบส่งต่อหลังยืนยันข้อจำกัด

ตัวแก้ cache/อายุโพสต์/คิวและ DOM ตรวจผ่าน tests แต่ **Facebook acceptance ยังไม่ผ่าน** เนื่องจากข้อจำกัดที่ Facebook ตอบจริง ต้องให้เจ้าของตรวจสถานะบัญชี/กลุ่มและยืนยันว่าใช้การคอมเมนต์ปกติได้ก่อนเปิดกฎใหม่ ไม่สรุปว่าเป็นการระงับถาวร ไม่คาดเดาระยะเวลาปลด และไม่เสนอการหลบข้อจำกัด

เจ้าของยืนยันภายหลังว่าบัญชีนี้ถูก Facebook จำกัดฟีเจอร์ชั่วคราว ให้แยกประเด็นนี้ออกจากบั๊กของ MY-BOT จึงยุติการทดสอบส่ง ไม่สลับบัญชีอัตโนมัติ และปิดงานอัปเดตระบบโดยรักษาการพักส่งไว้

ผลตรวจรุ่นสุดท้ายหลังอัปเดตและ restart จริง: manifest/background/sender/observer และ header ตรง 1.11.35, heartbeat หลัง restart รายงาน build 1.11.35, เว็บตอบ 200, worker และ workstation เป็น active, ขอบเขตยัง 10 กลุ่ม คิว active 87 / review 199 / blocked=false ณ จุดตรวจ ไม่แสดงรายการหมดอายุเป็นงานรอทำ ประวัติ uncertain 28 งานใน snapshot ก่อนรุ่น 34 ยังตรงทุกฟิลด์ที่ตรวจ ไม่มีการ replay งานเหล่านั้น

ถอด debugger drop-in และยืนยันพอร์ต 9223 ไม่ได้ listen แล้ว คง control และกฎเป็น paused ด้วยเหตุผล 1390008 คิวรอไม่ถูกลบ ไม่มีการกล่าวอ้างว่า Facebook ยืนยันการส่งสำเร็จขณะบัญชีติดข้อจำกัด
