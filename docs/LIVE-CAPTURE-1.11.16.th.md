## สิ่งที่แก้ใน MY-BOT

### จับการเปลี่ยนแปลงของฟีดที่ Facebook แสดงแล้ว

เดิม `content.js` อ่านครั้งแรกหลัง 4 วินาที และรอเลื่อนหยุด 8 วินาทีจึงอ่านอีก ไม่มี MutationObserver จึงไม่รู้ว่า React แทรกโพสต์ใหม่โดยไม่มีการเลื่อน

เปลี่ยนเป็น MutationObserver เฉพาะการเปลี่ยน DOM เกี่ยวกับ main/feed/article รวบการเปลี่ยนหลายครั้งใน wake 500 มิลลิวินาที อ่านครั้งแรกหลัง 1 วินาที มี fallback 15 วินาทีเมื่อแท็บแสดงอยู่ และตรวจอีกครั้งเมื่อกลับมาเห็นแท็บ ไม่คลิก ไม่ reload และไม่เรียก Facebook API

ส่งเฉพาะโพสต์ใหม่หรือเนื้อหาที่เปลี่ยน ใช้ post key ร่วมกับ scraper เดิม แบ่งครั้งละไม่เกิน 40 รายการ เก็บ pending ไว้จน worker ยืนยัน `accepted` ว่าข้อมูลเข้าคิว durable แล้ว ไม่ถือ HTTP/ข้อความตอบเก่าที่ไม่มี accepted ว่าสำเร็จ Retry คงเวลา observedAt แรกไว้

จำกัด pending 300 และ seen cache 1,000 รายการ ไม่ลบ pending ที่ยังไม่ได้ ack เพื่อเปิดช่องให้รายการใหม่ หาก snapshot ใหญ่กว่านั้นจะทยอยอ่านใหม่ระหว่างระบายคิว ตำแหน่ง DOM ที่หายไปก่อนถูก parse/รับเข้าคิวไม่ถือว่ามีการ capture สำเร็จแล้ว

เมื่อเปลี่ยนเซิร์ฟเวอร์/โทเคน/บัญชี/สถานะพัก จะยกเลิก cache ของบริบทเดิม แต่ heartbeat ที่เปลี่ยนเพียงเวลาไม่ทำให้ส่งทุกโพสต์ใหม่ซ้ำ แท็บของ background reader ยังคงใช้คิว/checkpoint เดิม ไม่แข่งขันกับ content capture หน้าเดียวกัน รองรับ pagehide/pageshow และ bfcache

### ไม่ทิ้งโพสต์ใหม่เพราะกลุ่มเพิ่งส่งข้อมูลมา

เดิม `forwardManual` มี gate 20 วินาทีต่อ source จำลองโค้ด HEAD ก่อนแก้ด้วยโพสต์ 2 รายการจากกลุ่มเดียวกัน ได้รับการส่งจริงเพียง 1 รายการ

เปลี่ยนเป็น dedupe รายโพสต์/เนื้อหา ผูกเซิร์ฟเวอร์ โทเคน บัญชี และ source จัดลำดับ snapshot ที่เข้าพร้อมกัน แล้ว mark หลัง `queueOutbox` สำเร็จเท่านั้น ส่ง ack ให้หน้าเว็บหลัง durable enqueue โดย flush เป็นงานแยกที่มี timeout/outbox recovery เดิม หาก storage เต็มจะไม่ ack และยังลองใหม่ได้ หากบัญชีพักจะเว้นการตรวจ ไม่เปิดงานหรือส่งคอมเมนต์

ยังคง batch threshold, transport ≤40, 20 parked/2 active readers, account pause, allowlist, quotas และช่วงตรวจกลุ่ม 3/10/30 นาทีเดิม ไม่เปลี่ยนความถี่เป็นยิงทุกกลุ่มทุกวินาที

### ส่งจากฐานข้อมูลขึ้นหน้า Feed ให้ครบและไม่รั่วการเชื่อมต่อ

SSE เดิมใช้เพียง `createdAt > last` และ take 20 จึงข้ามท้าย batch ได้เมื่อมีมากกว่า 20 แถวเวลาเดียวกัน เปลี่ยนเป็น cursor `(createdAt,id)` พร้อม order เดียวกัน ระบาย batch เต็มต่อใน 100 มิลลิวินาที และคงช่วงว่าง 2.5 วินาที ใช้ serial polling ไม่ให้ query ช้าทับกัน และหยุด timer เมื่อ request abort หรือ stream cancel

หน้า Feed เปิด EventSource หลัง ready เท่านั้น จึงไม่เหลือ connection จาก effect ที่ return ก่อน cleanup เมื่อ reconnect จะโหลดรายการกรองปัจจุบันใหม่ และไม่ให้ผล HTTP เก่าทับผลโหลดล่าสุด ยังต้องล็อกอินก่อนเปิด SSE ตามเดิม

SSE นี้เป็นการติดตามฐานข้อมูล MY-BOT ไม่ใช่ Facebook push การ reconnect/โหลดหน้าใหม่ใช้ query รายการตามปกติเป็นการซ่อมช่วงขาดหาย การส่ง event ไม่ใช่ durable event log และไม่ได้รับรองการตรวจพบ transaction ที่ commit ช้ากว่าตำแหน่ง cursor ทุกกรณี

## วิธีอ่านตัวเลขความเร็ว

แยกเวลา 3 ช่วง อย่าใช้ข้อความ “ไม่กี่วินาทีที่แล้ว” เพียงอย่างเดียว:

1. **เผยแพร่ → Facebook แสดง/เราอ่านพบ**: ขึ้นกับ Facebook, ลำดับฟีด, การเปิดแท็บ, Chrome throttling และรอบตรวจกลุ่ม `postedAt` ที่ parser อ่านอาจเป็นเวลาประมาณจากข้อความสัมพันธ์ ไม่ใช่เวลาเผยแพร่ที่ยืนยันระดับวินาที
2. **Parser อ่านพบ → MY-BOT ingest สำเร็จ**: รุ่นนี้ส่ง `observedAt` และวัด `capture_to_ingest` เป็นมิลลิวินาที เก็บไม่เกิน 200 ตัวอย่างต่อ web process ค่า p50/p95 อยู่ใน `requests.capture_to_ingest` ของ signed-in `GET /api/ai-queue` ไม่มี timestamp จะไม่แปลงเป็นศูนย์ ค่านาฬิกาอนาคต/คลาดเกิน 72 ชั่วโมงไม่ถูกนำมาสรุป และเครื่องกับเซิร์ฟเวอร์ต้องตั้งนาฬิกาตรงกัน
3. **Ingest → หน้า Feed เปลี่ยน**: รวมรอบ SSE, query รายการ และเครือข่าย เวลาตรวจ SSE 2.5 วินาทีไม่ใช่คำรับรอง end-to-end 2.5 วินาที

Metric observedAt เริ่มจากเวลาที่ parser อ่านพบ ไม่รวมเวลารอ 500 มิลลิวินาทีตั้งแต่ DOM เปลี่ยน เก็บในหน่วยความจำและหายเมื่อ process restart ไม่เพิ่มคอลัมน์ฐานข้อมูลหรือ migration และไม่แทนผล benchmark ต่อเนื่องบนเครื่องใช้งานจริง

## หลักฐานทดสอบ

- ก่อนแก้: ตัวจำลอง 2 โพสต์กลุ่มเดียวกันส่งได้ 1 โพสต์เพราะ gate 20 วินาที
- หลังแก้: โพสต์ที่สองเข้าคิวทันที ไม่ต้องรอ 20 วินาที; snapshot พร้อมกันไม่เพิ่ม durable copy ซ้ำ; เขียน storage ไม่สำเร็จยัง retry ได้
- DOM สังเคราะห์เพิ่มโพสต์โดยไม่เลื่อน: ส่งภายใน 600 มิลลิวินาทีของ fake clock ซึ่งรวม wake 500 มิลลิวินาที **ไม่ใช่ผลเวลา Facebook/เครือข่ายจริง**
- DOM 350 โพสต์ระบายครบทุก URL เป็น batch ไม่เกิน 40; ข้อความแก้ไขส่งใหม่; retry คงเวลาอ่านพบแรก; heartbeat ธรรมดาไม่ล้าง dedupe; bfcache กลับมาจับต่อได้
- Burst 25 แถว timestamp เดียวกันได้รับครบผ่าน SSE สังเคราะห์ และ query cursor บน PostgreSQL ทดสอบแยก ยืนยันการ abort/cancel และไม่ทับ slow poll
- ตรวจ metric ให้ข้ามเวลา browser ที่หายไป/อนาคต ไม่รายงานสุขภาพดีเป็นศูนย์

## นำไปใช้งาน

ต้องอัปเดตเว็บ/worker และ Reload extension ให้ตรง **1.11.16** เปิดกลุ่ม/Marketplace ที่ตั้งค่าไว้ตามปกติ เมื่อ Facebook แสดงเนื้อหาเพิ่มโดยที่แท็บมองเห็นอยู่ เส้นทางใหม่จะจับโดยไม่ต้องเลื่อน ส่วนกลุ่มที่ไม่ได้แสดงใน DOM ยังใช้ scheduler เดิม

ยังไม่ deploy, ไม่เปลี่ยน consent/โควตา/แพ็กเกจ ไม่เปิดคอมเมนต์จริง และยังไม่มีผล publish-to-ingest บน Facebook จริงที่ยืนยันระดับวินาที การเก็บครบทุกกลุ่มทันทีตั้งแต่เผยแพร่ยังไม่ใช่คุณสมบัติที่พิสูจน์แล้วของรุ่นนี้
