# ผลตรวจบอทแบบใช้กฎ: ฟีด โพสต์ และคอมเมนต์

ตรวจต่อจากการถอด AI โดยทบทวนเส้นทางรับข้อมูล → จัดประเภท/ให้คะแนน → กฎอัตโนมัติ → คิวคอมเมนต์ → การอนุญาตส่ง → การยืนยันผล รวมทั้ง worker, health และหน้า Feed ใช้ PostgreSQL ทดสอบแยกบน loopback และข้อมูลสังเคราะห์ ไม่มีการส่งคอมเมนต์จริง การประเมินนี้ครอบคลุมโค้ดใน working tree ก่อนนำขึ้นระบบจริง

ระบบใช้กฎ คำสำคัญ เงื่อนไขคัดออก คะแนน และแม่แบบข้อความได้โดยไม่เรียกโมเดล บอทไม่ได้เรียนรู้ความหมายใหม่หรือสร้างกฎใหม่เอง การปรับความแม่นยำยังต้องอาศัยข้อมูลที่เจ้าของตรวจและแก้ไข การถอด AI ไม่ได้ทำให้ Chrome, Facebook หรือเครือข่ายรับประกันเวลาเป็นวินาที

## ปัญหาที่พบและแก้ไข

| หลักฐาน/จุดเสี่ยง | ผลกระทบเดิม | การแก้ไข |
|---|---|---|
| ทดสอบรับโพสต์แล้วไม่เรียก callback หลังตอบ HTTP | โพสต์ถูกบันทึกแล้ว แต่คะแนน/กฎอัตโนมัติอาจไม่ทำต่อ | บันทึกสถานะงานใน Post พร้อม revision, token และเวลาลองใหม่; worker รับงานค้างซ้ำได้ |
| ทดสอบข้อความขยายระหว่าง callback เก่ายังรอ และการหมดอายุ claim | งานเก่าอาจยืนยันข้อความรุ่นใหม่ว่าประมวลผลครบ | ใช้ compare-and-set, lease renewal และตรวจเจ้าของ claim ก่อนจบงาน; งานเก่าไม่ล้างสถานะของรุ่นใหม่ |
| จำลองฐานข้อมูลปฏิเสธการเปลี่ยนสถานะโพสต์หลังจับกฎ | RuleHit อาจถูกบันทึกก่อน action สำเร็จ ทำให้ลองใหม่แล้วข้ามงาน | ทำ RuleHit, action, counter และ notification outbox ใน transaction เดียว พร้อมตรวจ revision/สถานะเจ้าของ |
| ทดสอบทำงานซ้ำหลัง lease หมด | อาจสร้างแจ้งเตือนในแอปหรือ outbox ซ้ำ | เพิ่ม unique dedupeKey และ insert แบบข้ามรายการเดิม; ไม่มีการส่งภายนอกภายใน transaction |
| ทดสอบ partial และ full text ของ URL เดียวใน batch | เก็บเฉพาะข้อความสั้นทั้งที่มีฉบับเต็ม | รวมก่อนเขียนฐานข้อมูล ให้ฉบับเต็มชนะ partial และเก็บข้อมูลเวลา/รูปที่ใช้ได้ |
| ทดสอบ claim เมื่อโพสต์ยังประมวลผลไม่ครบ | กฎคอมเมนต์อาจใช้คะแนน/ข้อมูลเก่า | scan และ final matching ปฏิเสธโพสต์ที่ processingState ยังไม่ done |
| ทดสอบคำว่า “ปล่อยแล้ว”, “ได้ช่างแล้ว” และข้อความปิดความต้องการ | keyword mode อาจตอบโพสต์ที่ไม่ต้องการแล้ว | ตรวจ closed intent ทุกโหมด โดยคงตัวอย่างคำขอที่ยังเปิดอยู่ |
| Feed SSE แจ้งเฉพาะแถวใหม่ | คะแนน/ข้อมูลที่คำนวณภายหลังของแถวเดิมอาจไม่ปรากฏ | เพิ่ม refresh เฉพาะแท็บที่มองเห็นทุก 5 วินาทีหลังคำขอก่อนจบ พร้อม cleanup; ไม่ยิงซ้อนเมื่อโหลดช้า |
| notification provider อาจใช้เวลานาน | หากใช้ lane เดียว งานกฎโพสต์อาจรอ | แยก consumer โพสต์ทุก 2 วินาที มี startup barrier, shutdown wait และ progress heartbeat |
| ทดสอบ cooperative yield | หากยืนยันทั้ง batch อาจทำให้งานที่ยังไม่ได้ทำหาย | ยืนยันเฉพาะ ID ที่ทำครบ ปล่อยส่วนที่เหลือให้รอบถัดไป |

หน้า Overview แสดงจำนวนงานโพสต์ค้าง งานรอลองใหม่ และอายุงานเก่าสุด public worker health ตรวจความสดของ consumer โพสต์ด้วย การคืน backup ล้าง token ของงานค้างเพื่อให้รับใหม่ได้ Migration ไม่เริ่มคอมเมนต์ ไม่เปลี่ยนโควตา และไม่รีเซ็ตงานส่งที่คลุมเครือ

## คะแนนหลังแก้ไข

คะแนนด้านโค้ดเป็นความเห็นทางวิศวกรรมจากเส้นทางที่ตรวจและ regression tests ไม่ใช่เปอร์เซ็นต์ความสำเร็จบน Facebook และไม่ใช่ผลรับรอง uptime

| ส่วน | คะแนน /10 | สิ่งที่ยังต้องพิสูจน์ |
|---|---:|---|
| รับ/เก็บโพสต์และรักษาข้อความฉบับเต็ม | 9.2 | อัตราเก็บครบจากกลุ่มจริงและ DOM ปัจจุบัน |
| ประมวลผลกฎและกู้คืนงานโพสต์ | 9.3 | throughput และอายุคิวเมื่อโหลดจริงต่อเนื่อง |
| คัดกรองคอมเมนต์และตรวจข้อมูลล่าสุด | 9.2 | precision/recall จากตัวอย่างจริงที่เจ้าของติดป้ายกำกับ |
| ป้องกันส่งซ้ำ/ผิดบัญชี/งานคลุมเครือ | 9.5 | การยอมรับบนบัญชีจริงภายใต้ความยินยอมแยกต่างหาก |
| transaction และแจ้งเตือนจากการทำงานซ้ำ | 9.3 | ไม่รับรอง exactly-once ของผู้ให้บริการส่งข้อความภายนอก |
| Feed และการมองเห็นงานค้าง | 9.2 | ความหน่วงเครือข่ายและข้อมูลเครื่องจริง |
| การกู้คืนและแบ่งงานของ worker | 9.2 | การสังเกตทำงานจริง 24–72 ชั่วโมง |
| ความต่อเนื่องหลายวันบนระบบจริง | ยังไม่รับรอง | ยังไม่มี soak test จริงหลังแก้ |
| ความตรงเวลาเป็นวินาทีตายตัว | 7.0 | Chrome alarms, หน้า Facebook และเครือข่ายไม่ใช่ hard real time |
| ความพร้อมเครื่องที่ตรวจ | 3.0 | baseline doctor พบ SQLite URL เดิม, DB ไม่พร้อม, ไม่มี extension token และเว็บยังไม่รัน |

จึงยังไม่สามารถให้ 9++ ทุกส่วนหรือเต็ม 10 อย่างมีหลักฐาน แม้ส่วนโค้ดที่แก้มีความทนทานเพิ่มขึ้น งานที่ไม่แน่ใจว่าส่งแล้วหรือยังจะหยุดให้เจ้าของตรวจ แทนการส่งซ้ำเอง นี่เป็นข้อจำกัดที่ต้องรักษาไว้

## การนำไปใช้และเกณฑ์ยอมรับที่ยังเหลือ

ต้องกำหนด PostgreSQL ของเจ้าของให้ถูกต้องก่อน แล้วหยุดโฮสต์ที่ใช้ฐานร่วมกันเพื่อรัน `npm run db:migrate` ตามขั้นตอนอัปเดต จากนั้น build/restart และโหลดส่วนขยาย 1.11.26 ใหม่ การเปลี่ยนนี้ยังไม่ได้ใช้กับฐานข้อมูลจริง ไม่ได้ deploy และไม่ได้ส่งคอมเมนต์ Facebook

ก่อนยกระดับคะแนนการปฏิบัติงาน ต้องให้ doctor ไม่มี FAIL, health ผ่าน, worker/ส่วนขยายรุ่นตรงกันและ heartbeat สด แล้วเก็บผลอ่านอย่างเดียว 24–72 ชั่วโมง: จำนวนโพสต์เทียบรายการที่ตรวจเอง, งานค้างเก่าสุด, recovery เมื่อเครือข่ายขาด, latency p50/p95/p99 และ memory/tab growth การวัด observed-to-ingest ต้องแยกจาก publish-to-capture ใช้ตัวอย่างจริงที่เจ้าของตัดสินว่าควร/ไม่ควรตอบเพื่อวัด precision และ recall แทนการอ้างความแม่นยำจากข้อความสังเคราะห์

การทดสอบส่งจริงต้องได้รับอนุมัติแยกตามข้อกำหนด repository และใช้กฎ/บัญชี/กลุ่มที่เจ้าของยินยอมเท่านั้น การตรวจครั้งนี้ไม่เปิดสวิตช์ดังกล่าว

## ผลตรวจรอบสุดท้าย

- `TEST_DATABASE_URL` ชี้ PostgreSQL ทดสอบบน loopback พอร์ต 55439: `npm.cmd test -- --no-file-parallelism` ผ่าน **937 tests**, ข้าม 8 ตามแพลตฟอร์ม/เครื่องมือ; 118 test files ผ่านและ 2 ข้าม ไม่มีข้อผิดพลาด ใช้เวลา 147.71 วินาที
- `npm.cmd run doctor` บน environment จริงยัง **FAIL 3 / WARN 1**: DATABASE_URL เป็น SQLite, DB ไม่พร้อม, ไม่มี token และพอร์ต 8001 ว่าง ไม่ได้เปลี่ยน secrets ของเจ้าของ
- `npm.cmd run build`, `npx.cmd tsc --noEmit` และ `git diff --check` ผ่าน
- Chrome โปรไฟล์ทดสอบแยก: Settings, Feed, Auto-comment, Overview ผ่าน ไม่มี JavaScript page errors; API AI ที่เลิกใช้ตอบ 410; สถานะคอมเมนต์ยังหยุดอยู่ มีเพียง browser verbose hints เรื่องแบบฟอร์มเดิม
- ปิด Chrome และเซิร์ฟเวอร์ทดสอบแล้ว พร้อมลบ schema ชั่วคราว ไม่เปลี่ยนข้อมูลเจ้าของ ไม่ commit/push/deploy
