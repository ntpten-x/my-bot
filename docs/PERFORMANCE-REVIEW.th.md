ไม่ได้แก้พฤติกรรมแอป ไม่หยุดโปรเซส ไม่ส่งโพสต์ทดสอบหรือแจ้งเตือนภายนอกเพื่อทดสอบโหลด การรัน doctor มีการตรวจบริการและ embedding ตามคำสั่งเดิมของโครงการ

## ลำดับปรับปรุง

### 1. ตรวจงาน AI ที่ retry ซ้ำ และแสดงเหตุผลที่ตรงกับงานจริง — เร่งด่วน

หลักฐานจริง: 5/6 โพสต์ยังอยู่ rules พร้อมงาน pending ที่ attempts=8 ขณะตรวจ ยังไม่ได้ยืนยันสาเหตุรายงาน จึงไม่สรุปว่า timeout หรือ provider ล่ม

หลักฐานโค้ด: `src/lib/ai/queue.ts:180` ใช้ `outcome.errors[0]` เป็นเหตุผล retry ซึ่งอาจเป็นข้อความข้าม provider ที่ไม่ได้ตั้งค่า แทนความผิดพลาดของ provider ที่รับงานจริง

ข้อเสนอ: แสดงเหตุผลแยก provider และเวลาลองล่าสุด ตรวจหนึ่งงานตั้งแต่ enqueue ถึงผล classify แล้วแก้จากสาเหตุจริง แยกกรณีตั้ง rules โดยเจตนาออกจาก AI ล้มเหลว เพิ่มสถานะพักงาน/ลองใหม่ด้วยมือหลังผิดซ้ำตามเกณฑ์ แทนลองไม่สิ้นสุดโดยไม่มีภาพรวม

### 2. อย่าตั้ง done ทั้งชุดเมื่อ AI ตอบไม่ครบ — เร่งด่วน

เส้นทาง: `src/lib/pipeline/classify.ts:94` เติม `ruleItem` ให้โพสต์ที่ provider ตอบขาด แต่ส่ง provider ระดับชุด → `src/lib/ai/queue.ts:135` ตรวจ provider ของชุด → บันทึก aiProvider เดียวให้ทุกผล (`:147`) และตั้งทุกงาน done (`:156`)

ตัวอย่าง: ส่ง 10 โพสต์ AI ตอบได้ 1 แล้ว provider ที่เหลือล้มเหลว อีก 9 โพสต์ใช้ rules แต่ถูกบันทึกเสมือน AI สำเร็จ ผลคือหลุดจากคิว retry และสถิติ provider คลาดเคลื่อน พบจากการไล่โค้ด ยังไม่ได้พิสูจน์ว่าเกิดกับข้อมูลปัจจุบัน

ข้อเสนอ: คืนสถานะ/provider ต่อโพสต์ ตั้ง done เฉพาะรายการที่ AI สำเร็จหรือ cache ที่ยอมรับได้ แล้ว retry รายการที่เหลือ เพิ่ม integration test กรณี partial response

### 3. ย้าย embedding ออกจากคำขอรับโพสต์ และใช้เวกเตอร์เดิม — สูง

เส้นทาง: `src/lib/ingest.ts:146` รอ enrichPosts → `src/lib/smart/enrich.ts:68` เรียก embedText ทีละโพสต์ → หลัง AI สำเร็จ queue เรียก enrichPosts อีกครั้ง (`src/lib/ai/queue.ts:151`) โดยไม่ตรวจเวกเตอร์เดิม

ผล: request รับโพสต์รอโมเดลและงานให้คะแนน การสร้างเวกเตอร์ซ้ำเสียเวลา และความล้มเหลวของ embed ในการ enrich รอบหลังอาจเขียนทับเวกเตอร์เดิมเป็นข้อความว่าง

ข้อเสนอ: ใน request บันทึกโพสต์ ให้คะแนนจากกฎ และ enqueue เท่านั้น สร้าง embedding ใน worker ใช้ค่าที่มีเมื่อข้อความและโมเดลยังตรงกัน และเก็บค่าเดิมเมื่อ provider ล้มเหลว ไม่จำเป็นต้องเพิ่มระบบคิวภายนอก

### 4. แยกจังหวะคิว AI จากรอบดึงแหล่งข้อมูล — สูงเมื่อปริมาณเพิ่ม

หลักฐาน: `src/lib/ai/queue.ts:74` เลือกครั้งละ 10; `src/worker/index.ts:63` เรียกเพียงครั้งเดียวต่อ tick หลัง source fetch/summary/backup และ `:73` ตั้ง cron ทุกนาที มี guard กัน tick ซ้อน

โดยโครงสร้างรอบปกติรับได้ไม่เกินประมาณ 10 งานต่อนาทีเมื่อทำงานเสร็จในรอบ และลดลงเมื่อรอบนานเกินนาที ตัวเลขนี้เป็นขอบเขตจากโค้ด ไม่ใช่ผล load test; คิว 100 งานต้องใช้เวลาระดับสิบนาทีได้แม้ AI ตอบเร็ว

ข้อเสนอ: ให้ consumer คิวทำต่อเมื่อยังมีงานพร้อม พร้อมพักตาม backoff แยกจากรอบ fetch และคงการประมวลผลชุดเดียวก่อน วัดจริงก่อนเพิ่ม concurrency โดยเฉพาะเมื่อใช้ GPU ร่วมกับ embedding

### 5. แก้ขอบเขต dedupe ที่วนตรวจเฉพาะโพสต์เก่า — กลาง

หลักฐาน: `src/lib/smart/enrich.ts:171` เรียง createdAt จากเก่าไปใหม่ แล้ว take 500 (`:172`) และเปรียบเทียบแบบลูปซ้อน เมื่อมีเกิน 500 โพสต์ที่ยังไม่ถูกยุบในขอบเขตที่เลือก โพสต์ใหม่จะไม่เข้า truncated-capture comparison

ข้อเสนอ: รับ IDs ของโพสต์ใหม่แล้วค้นผู้สมัครในแหล่งเดียวกัน หรือใช้ cursor ตรวจย้อนหลังเป็นชุด การเปลี่ยนเป็นเลือกล่าสุดอย่างเดียวช่วยเฉพาะข้อมูลใหม่ แต่ยังไม่แก้ความครบถ้วนของข้อมูลเก่า

### 6. แจ้งขอบเขตผลค้นหาและลดข้อมูลที่อ่าน — กลาง

หลักฐาน: `src/app/api/posts/route.ts:69` จำกัด keyword candidates ที่ 200 ล่าสุด และ `:76` จำกัด semantic candidates ที่ 200 ล่าสุด จากนั้นรายงาน total จาก pool นี้ ผลเก่าที่ตรงมากอาจไม่ถูกนำมาจัดอันดับ และ total ไม่ใช่จำนวนตรงทั้งหมดในฐานข้อมูล

ข้อเสนอ: keyword search นับและแบ่งหน้าจากฐานข้อมูล; semantic search กำหนดช่วงข้อมูลให้ชัดหรือขยาย candidate retrieval ตามความจำเป็น แสดงข้อจำกัดให้ผู้ใช้เข้าใจ ใช้ select เฉพาะฟิลด์ที่ต้องใช้ก่อนจัดอันดับ เพราะ include ปัจจุบันอ่านเวกเตอร์และความสัมพันธ์มาด้วย

### 7. เพิ่มการทดสอบเส้นทางใช้งานจริงและตัวชี้วัด — กลาง

Tests ปัจจุบันผ่าน แต่ตัวอย่าง `tests/pipeline/audit.test.ts:27` ตรวจค่าคงที่ STUCK_JOB_MS และการจำกัด OCR ตาม process ไม่ได้จำลองการกู้คืนงานค้างจริง

ข้อเสนอ: เพิ่ม integration tests ที่คุ้มค่า ได้แก่ ingest → enqueue → classify → done, partial response → retry, provider ล้มเหลว และรักษา embedding เดิม เก็บเวลารอคิวแยกจากเวลาประมวลผล พร้อม pending age, success/retry rate และ p50/p95 ของ ingest/search ไม่ใช้คะแนนสุขภาพเป็นตัวแทน throughput

ความแม่นยำ buyer/seller/ad ยังประเมินไม่ได้จาก 6 โพสต์และ feedback=0 ควรทำชุดตัวอย่างภาษาไทยที่เจ้าของติดป้ายคำตอบ แล้ววัด precision/recall โดยเฉพาะ buyer ก่อนปรับ prompt หรือเปลี่ยนโมเดล

## การตรวจ build และข้อจำกัด

`npm run build` หยุดที่ Prisma generate เพราะ Windows ไม่ยอม rename `query_engine-windows.dll.node` จึงยังไม่ได้ยืนยัน Next production build ไฟล์อาจถูกโปรเซสใช้งานอยู่ แต่ยังไม่ได้พิสูจน์สาเหตุ ไม่ได้หยุดแอปที่เจ้าของใช้งาน ควรตรวจโปรเซสที่ใช้ไฟล์และ build ในช่วงอัปเดตหรือ checkout แยก

ไม่ได้แก้โค้ดแอปหรือ commit ในการตรวจนี้ `.env.example` มีการแก้ค้างตั้งแต่ก่อนเริ่มและไม่ได้แตะต้อง เพิ่มสคริปต์ `scripts/audit-performance-local.mjs` สำหรับอ่านสถิติรวมซ้ำด้วย `node scripts/audit-performance-local.mjs`; สคริปต์ไม่แสดงคีย์ เนื้อหาโพสต์ หรือ raw error และไม่แก้ฐานข้อมูล

ข้อเสนอสำหรับรอบถัดไป: แก้ความถูกต้องของสถานะ AI และงาน retry ก่อน แล้วลดเวลารับโพสต์ด้วยการย้าย embedding ไป worker หลังจากนั้นวัด throughput ด้วยข้อมูลทดสอบในฐานข้อมูลแยก
