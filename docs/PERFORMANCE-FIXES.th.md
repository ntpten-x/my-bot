# การแก้ไขประสิทธิภาพและคิว AI

วันที่ 2 พฤศจิกายน 2026 — ต่อจาก [รายงานตรวจ](PERFORMANCE-REVIEW.th.md)

## ปัญหาและสาเหตุ

ก่อนแก้มีโพสต์ 6 รายการ โดย 5 รายการยังใช้กฎและ retry มาแล้ว 8 ครั้ง ข้อความผิดพลาดที่เก็บไว้คือการข้าม Gemini เพราะไม่มีคีย์ ซึ่งไม่ได้สะท้อนการเรียก provider ที่รับงานจริง การ probe แบบไม่เขียนโพสต์พบ Ollama หมดเวลาในกรอบ 12 วินาที แต่ Groq รับช่วงต่อและตอบครบได้ จึงไม่ใช่กรณี AI ทุกตัวใช้งานไม่ได้

อีกปัญหาคือ classifier คืน provider ระดับชุด แม้บางโพสต์ได้รับเพียงผลจากกฎ ทำให้ queue สามารถตั้งงานเหล่านั้นเป็น done ได้ ข้อผิดพลาดนี้ยืนยันด้วย regression test ที่ล้มเหลวก่อนแก้ และ integration test ที่ส่ง partial response ผ่าน provider จริงโดยจำลองเฉพาะ HTTP

การรับโพสต์เรียก embedding แบบเรียงทีละโพสต์ และ queue เรียกสร้างซ้ำหลัง AI เสร็จ รวมถึงอาจเขียนเวกเตอร์เดิมทับด้วยค่าว่างเมื่อ provider ล้มเหลว ส่วน worker เดิมทำ AI เพียงชุดเดียวหลัง fetch/summary/backup ในแต่ละนาที

## สิ่งที่เปลี่ยน

| คำแนะนำเดิม | การแก้ไข |
| --- | --- |
| เหตุผล retry และงานวนซ้ำ | เก็บชื่อ provider พร้อม error จริง เคารพ Retry-After ไม่มีการนอน retry HTTP 429 ซ้ำใน provider; ผิดครบ 10 ครั้งเป็น failed และลองใหม่ด้วยมือได้ |
| Partial AI response | ส่ง providersById ต่อโพสต์และตั้ง done เฉพาะโพสต์ที่ได้ผล AI/cache รายการที่ขาดยัง retry |
| เลือก rules โดยเจตนา | เป็น skipped ไม่เสีย attempts; เปลี่ยนเป็น AI แล้ว worker รับต่อ |
| เปิดแอปซ้ำ | รักษา backoff/failed เดิม; ปุ่ม retry และ db:backfill-ai รีเซ็ตเฉพาะรายการที่ยังไม่มีผล AI โดยไม่แย่งงาน running |
| รับโพสต์ช้า | Request ทำกฎ/บันทึก/เข้าคิว; embedding และการส่งแจ้งเตือนภายนอกอยู่ใน worker |
| Embedding ซ้ำ/ข้อมูลหาย | ใช้ hash ข้อความและการตั้งค่า พร้อม identity ของ provider/โมเดลจริง ใช้ของเดิมเมื่อเข้ากัน เก็บค่าเดิมเมื่อผิดพลาด แล้วเลื่อน retry 5 นาที |
| เวกเตอร์ข้ามโมเดล | ไม่เทียบ semantic/dedupe/centroid ข้าม embedding space; cosine ปฏิเสธขนาดต่างกัน |
| คิว AI ช้า | Consumer ตรวจทุก 2 วินาทีและทำต่อเมื่อมีงานพร้อม แยกจาก maintenance; AI/embedding ยังเรียงใน consumer เดียวเพื่อลดการแย่งโมเดล |
| งาน running ค้าง | Claim ใน transaction พร้อม heartbeat 30 วินาที; คืนงานเมื่อ heartbeat เก่าเกิน 2 นาที |
| ตรวจข้อความตัดเฉพาะ 500 โพสต์เก่า | Cursor อ่านครบทุกชุดและจัดกลุ่มตามแหล่ง/ข้อความขึ้นต้นก่อนเปรียบเทียบ ทำใน maintenance; exact-text repair ก็ตรวจครบทุกกลุ่ม |
| ค้นได้แค่ 200 รายการ | Keyword count/pagination จากฐานข้อมูลทั้งหมดตามตัวกรอง เรียงคะแนน/วันที่; semantic ใช้ผู้สมัครล่าสุดประเภทละ 1,000 และแจ้งขอบเขตชัดเจน |
| อ่านข้อมูลค้นหาหนักเกินไป | Semantic ดึงฟิลด์จัดอันดับก่อน แล้วอ่านความสัมพันธ์เต็มเฉพาะหน้าที่แสดง |
| ขาดตัวชี้วัด | แดชบอร์ดอัปเดต 15 วินาที แสดงสถานะ/อายุคิว/ข้อผิดพลาด/เวลา retry, p50/p95 และสัดส่วนงานที่จบสำเร็จ; GET /api/ai-queue ต้องล็อกอิน |
| ขาดเกณฑ์วัดความแม่นยำ | เพิ่ม evaluator ที่แสดง precision/recall ราย intent และรับไฟล์ที่เจ้าของติดป้ายคำตอบได้ |

การแจ้งเตือนภายนอกใช้แถวภายในของ Notification เป็น outbox ขนาดเล็ก เมื่อบางช่องทางล้มเหลวจะลองเฉพาะช่องทางที่ยังไม่ได้ส่ง และพักหลัง 5 ครั้ง ไม่มีการเพิ่มระบบคิวภายนอกหรือ dependency ของแอป

## การยืนยัน

- `npm test`: 69/69 ผ่าน รวม SQLite integration 13 กรณี ใช้ฐานข้อมูลชั่วคราวและ HTTP จำลอง ไม่มีการส่ง notification จริงจาก tests
- Integration ครอบคลุม ingest → enqueue → classify → done, partial response, paused/manual retry, rules mode, stale recovery, 12 งานต่อเนื่อง, Retry-After, embedding reuse/failure, centroid ต่างโมเดล, dedupe เกิน 500 โพสต์และ 50 กลุ่ม, keyword 235 รายการ และ semantic 1,010 รายการ
- Prisma migrate diff ไม่พบความต่างระหว่างฐานข้อมูลกับ schema
- ตรวจ Chrome ผ่านข้อมูล UI จำลองแยกพอร์ต 8002: dashboard, retry button, search scope, desktop/mobile ไม่มี pageerror หรือ horizontal overflow
- `npm run evaluate:classifier` ผ่านตัวอย่างแต่งขึ้น 20 ข้อ ผลนี้เป็น smoke check จากกรณีที่ระบบรู้จักอยู่แล้ว ไม่ใช่ความแม่นยำบนข้อมูลกลุ่มจริง
- `npm run build` รอบสุดท้ายผ่าน รวม Prisma generate, compile, lint, type check และ static generation หลังหยุดโปรเซสที่ล็อก DLL
- เปิด production web/worker กลับแล้ว `npm run doctor` FAIL=0, WARN=2 (Gemini ไม่ได้ตั้งค่า เป็น optional)
- ตรวจข้อมูลจริงเวลาโดยประมาณ 21:51 น.: done 6/6, pending=0, failed=0, embedding ว่าง=0; aiProvider Groq 5 และ Ollama 1 ตามผลที่บันทึกไว้
- หลังเปิดพบงานเดิม failed 4 งานจาก partial response ครบ 10 attempts จึงรัน `npm run db:backfill-ai` แล้ว worker ประมวลผลทั้ง 4 จบในรอบใหม่ได้ ไม่ต้องแก้สถานะด้วย SQL
- Public health HTTP 200 ทั้ง 5 samples ล่าสุดประมาณ 7–45 ms ตัวเลขนี้ไม่ใช่เวลาค้นหาหรือรับโพสต์

ก่อน migrate ได้สำรองฐานข้อมูลไว้ใน `data/backups/before-performance-1793629072516.db` และไม่ได้แก้ `.env` หรือการเปลี่ยนแปลงเดิมใน `.env.example` ไม่มี commit ในงานนี้

## ขอบเขตของผล

ยังไม่มีผล load test บน GPU กับข้อมูลจำนวนมาก จึงไม่อ้างเปอร์เซ็นต์ความเร็วที่เพิ่มขึ้นหรืออัตราโพสต์ต่อนาทีจริง การค้นหาด้วย contains ยังมีต้นทุนตามจำนวนข้อมูล และการตรวจ capture ยังต้องอ่านโพสต์ครบใน maintenance แม้เปรียบเทียบเฉพาะกลุ่มที่ขึ้นต้นตรงกัน ควรวัดก่อนเพิ่ม full-text/vector index หรือเปลี่ยนฐานข้อมูล

เวลารอคิวหมายถึงเวลาตั้งแต่ enqueue รอบล่าสุดถึงเริ่ม attempt ล่าสุด รวม backoff ส่วน p50/p95 ของ request เป็นตัวอย่างในหน่วยความจำ 200 รายการต่อโปรเซสและรีเซ็ตเมื่อเริ่มโปรเซสใหม่ อัตราสำเร็จนับเฉพาะงาน done/failed ใน 200 งานที่อัปเดตล่าสุด ไม่ใช่อัตราสำเร็จครั้งแรก

สิ่งที่ยังต้องใช้ข้อมูลจากเจ้าของคือชุดป้ายคำตอบที่สะท้อนกลุ่มจริง ดูวิธีรัน evaluator และการจัดการคิวใน [คู่มือ](SETUP.th.md)

## เหตุผลที่ tests เดิมไม่พบ

Tests เดิมเน้นฟังก์ชันกฎ/ค่าคงที่และ helper ไม่มีการยืนยันการเปลี่ยนสถานะงานจริงใน SQLite เมื่อ provider ตอบบางรายการ รวมถึงไม่มีข้อมูลเกินเพดาน candidate/dedupe การเพิ่ม integration tests ข้างต้นครอบคลุมรอยต่อเหล่านี้แล้ว
